# Job discovery (find work → the website queue; reads only, NEVER applies)
The stage BEFORE the queue. `discover.js` (SW; `importScripts` AFTER lib.js — it uses `canonicalJobUrl`) sweeps three sources for recently-posted jobs the operator hasn't applied to, scrapes a JD for each, and **RETURNS them — it writes nothing**; the WEBSITE persists them (`saveDiscovered` → `queue_items`). Entry: `AP_DISCOVER_JOBS` (the `/app/run` Discover button) + `AP_DISCOVER_RECON`; popup `RUN_DISCOVER` / `RUN_DISCOVER_RECON` are the dry-run/debug path (log-only, queues nothing). `[DISCOVER]` in the SW console.

- **Three sources, cheapest substrate that works.** **simplify** = the SimplifyJobs/Summer2026-Internships board's PUBLISHED `listings.json` (`company_name/title/url/locations/terms/active/is_visible/date_posted` unix-s) — a plain `fetch`, no tab, and a REAL posted date; only `active && is_visible` rows survive (inactive = a CLOSED posting). **linkedin / handshake** = the operator's LOGGED-IN session read from a real unfocused tab **through their own cookies** — no API key, no credential handling, and discovery NEVER attempts a login (operator decision 2026-07-26).
- **ONE DRIVER FOR BOTH BOARDS (2026-07-30).** Once both were traced they turned out to have the same shape, so `discoverFromBoard(source, opts)` + a `BOARD_CONFIG` entry per board does LinkedIn and Handshake identically — same paging, filtering, detail read, dedup and logging, so a fix or a bug is never in only one of them. Both use the rendered **SEARCH PAGE** for discovery and the board's own **JSON RECORD** per posting. The page is the search substrate on BOTH, not a fallback: Handshake's JSON index ignores every filter param (its total never moves), and LinkedIn's page runs its newer SEMANTIC search which returns visibly better matches than its keyword API for the same words. Both pages paginate (LinkedIn `start=N`, Handshake `page=N`) — that's what lets a later sweep reach past what's already queued.
- **⚠ THE OLD LINKEDIN SCRAPERS WERE REFUTED, NOT TIGHTENED (2026-07-30).** They shipped "structure-first" (written blind — no authenticated session at build time) and the first real trace found **all ~30 selectors matching ZERO**: LinkedIn shipped a server-driven-UI rewrite where result cards are `div[role=button]` with **no anchor inside at all**, and every class is a rotating build hash. The scrapers are rebuilt on the two stable, semantic, id-carrying anchors the trace did find — **`componentkey="job-card-component-ref-<id>"`** (LinkedIn) and **`data-hook="job-result-card | <id>"`** (Handshake) — verified 25/25 and 24/25 cards live. Full detail incl. the JSON contracts: `docs/dom-patterns.md` 2026-07-30.
- **Fields come from reading order, and that bit once.** The SDUI card has no per-field selectors, so title/company/location are its text LINES — and the leading a11y summary varies (`"Title (Verified job)"` / `"Title"` / absent). A consecutive-dedupe misses the first shape, which **shifted every field by one on exactly the verified postings** (company took the title, location took the company) — wrong data that still looks plausible. The split is therefore done SW-side by the pure, regression-pinned **`linkedInFieldsFromLines`** (the injected scraper returns raw `lines`), tested against all three real card fixtures.
- **The DETAIL pass reads each board's own JSON record — no tab, no clicks (2026-07-30).** Replaces the old card-clicking pane reader. One request per posting gives the JD text, the exact posted epoch, whether it's still open, the applicant count, and — the reason it exists — **the employer's real application URL as a TYPED field**: LinkedIn `applyMethod["…OffsiteApply"].companyApplyUrl`, Handshake `job_apply_setting.external_url`. Board-only applications (Easy Apply / Quick apply) are identified by that field's SHAPE, not by matching rendered text. Nothing is clicked, so the Apply button can never be touched, and there's no dependence on a pane painting (which is what made the old path unreliable in a background tab). A failed record read is NON-FATAL — the job still queues and falls through to `fillMissingDescriptions` (ONE reused tab, `scrapeJobPosting`, one CDP attach across all navigations).
- **⚠ `job_apply_setting`, NOT `external_apply_link`, is Handshake's apply config.** The record carries both and the obvious-looking `use_external_apply_link`/`external_apply_link` pair is LEGACY — `false`/`null` on **all 30** live postings sampled, *including* ones that plainly apply offsite. Believing it reported "0% of Handshake jobs have an employer link", which would have silently reduced the whole source to zero once board-only postings are skipped. Read correctly, **33%** carry a real link (Greenhouse/Workday/Google Careers/Paylocity/Tesla). Regression-pinned both directions.
- **⚠ Date-sorting LinkedIn's search API destroys keyword relevance.** `sortBy:List(DD)` drops every promoted row (which looked like a free win, and an earlier build had it permanently on) but returns the newest internships of ANY kind — "embedded software intern" came back as *EH&S Intern* / *Audit Intern* / *Finance Intern*. Relevance returns Skydio/Anduril/Blue Origin/Palantir. So: **relevance for WHAT, our own `scoreDiscovery` for the ORDER, and promoted rows penalised** rather than sorted away. Unit-pinned.
- **Arbitrary ATS hosts without an `<all_urls>` grab.** `discoverReadPage` tries `chrome.scripting` (for the hosts we DO take — linkedin / joinhandshake / raw.githubusercontent) and falls back to **CDP** for arbitrary employer pages, since `chrome.debugger` isn't host-gated (the same invariant the Workday walk relies on). **`discoverInFlight` ⟷ `runInFlight` are MUTUALLY EXCLUSIVE** — not politeness: cdp.js tracks ONE `cdpTabId`, so a discovery CDP read would clobber a running walk's attach mid-fill.
- **`discoveryJobKey` — dedup identity (LOCKSTEP `discover.js` ↔ `web/lib/discover.ts`).** Extends `canonicalJobUrl` with board ids (`linkedin:`/`handshake:`/`greenhouse:`/`lever:`/`ashby:`). **Ordering is load-bearing:** a Workday posting keys through `canonicalJobUrl` FIRST so a Simplify-board job (whose url IS the employer's Workday link) matches the `applications.job_key` written after applying — that's what makes "not yet applied to" hold across tables. The site sends `knownKeys` (applications incl. soft-deleted + all queue rows, each contributing stored AND freshly-derived keys) so the sweep skips them BEFORE spending a tab open; `saveDiscovered` **re-derives every key server-side** (a client-supplied key is IGNORED) with the partial unique index on `(user_id, job_key)` as the race backstop.
- **Search TARGETING — never a blank search (2026-07-29).** `buildDiscoverQuery` composes the keywords: an explicit box wins, else they're DERIVED from the profile's `education[0].field_of_study` (the run page passes it in), plus "intern" when the Internships box is ticked (deduped — a query already saying intern isn't doubled). **A keyword-less LinkedIn URL is its RECOMMENDED FEED, not a search** — that's what made the first live sweep return default suggestions — so the URL builders **RETURN "" on empty keywords** and the source is skipped with a note. **Season** (`discoverTermLabel(cycle, year)` → "Summer 2026") filters the Simplify feed EXACTLY (its rows carry the term verbatim); on the keyword boards it's advisory only, which the UI says. The composed search is RETURNED (`out.search`) + logged + previewed in the panel, so what ran is never a mystery. **The board results are NOT re-filtered on keywords** — the board already searched the full posting text, and AND-ing tokens against a card's short title threw away correct hits; the local `matchesDiscoverQuery` (now ANY-token, stopword-stripped) applies ONLY to Simplify, which has no server-side search.
- **The Internships checkbox drives the BOARDS' own filters, not just the keyword (2026-07-30, operator's call — one control, not two).** Ticked ⇒ `experience:List(1)` on LinkedIn and `jobType=3` on Handshake. This is the single highest-value filter observed: 127 → 25 results, every row a genuine internship or co-op.
- **LOCATION: free text, resolved through each board's OWN typeahead, then cached.** No hardcoded country anywhere in the sweep — the web panel seeds its box from the profile's `personal_info.country`, and `DISCOVER_DEFAULT_LOCATION` is a last resort that gets REPORTED when used. Neither board's location token is constructible (LinkedIn needs a numeric `geoId`; its API returns HTTP 500 for a place name — Handshake needs a JSON place blob with a Mapbox-style id + lat/lon + radius), and LinkedIn's typeahead is an **opaque RSC server action**, so `resolveBoardLocation` drives the real control once per (board, text) and reads the token off the board's own rewritten URL, caching it in `chrome.storage.local.discoverGeoCache`. Any city/state/country works, nothing is guessed. **It must use TRUSTED CDP input:** synthetic events — including a full pointer sequence with pointerId/isPrimary/detail — do NOT open LinkedIn's location panel (the same lesson already recorded for the Workday auth form). Two more traps, both live-verified: LinkedIn's box is a **contenteditable div** (`componentkey="LocationTypeahead_TextEditor"`), not an `<input>`, and its suggestions are **`<a>` rows** inside `componentkey="semanticSearchBoxLocationList"` with **no `role="option"`/`listbox"` at all**. A failed resolve searches WITHOUT a location filter and says so — it never silently searches somewhere else.
- **SETTLE ON A STABLE CARD COUNT, NOT ON "SOME CARDS EXIST".** `pollForCards` first returned on the first non-empty read and captured **3 cards of 25** — both boards mount progressively, so "some cards exist" is true long before the page is done. The sweep reported `scanned 3` and silently missed 22 postings; a quiet under-read is worse than an error. It now accepts only a non-zero count that reads the same twice (or a full page), on per-board budgets (LinkedIn ~8s to render, Handshake 15–25s even foreground). Fourth instance of one lesson — JD page, form pages, review page, now board lists: **never scan a progressively-rendered page without settling it first.**
- **TWO BUDGETS, BECAUSE THE COSTS DIVERGED.** `maxJdOpens` was 10 because a JD once meant OPENING A TAB. A board record is now one cheap same-origin fetch, so `maxRecords` (25) covers a whole page of candidates while `maxJdOpens` (10) still bounds real reader-tab loads. Sharing one budget had a concrete consequence: records were read for the NEWEST 10 while the queue kept the BEST N — different sets — so a queued job could arrive with no JD and no employer link (observed live: an Amazon posting, `resolved:false`). Enriching every candidate also makes the ranking honest, since score depends on the JD and the applicant count. Related: the record budget is spent AFTER a pre-rank on card-only signals, so it goes to the jobs most likely to be queued.
- **SCRAPE WIDE, QUEUE NARROW (2026-07-30, operator's design).** The sweep pages through several pages per board (`maxPages`), then queues only the best `queueLimit` (default 10, or "all"). Ranking is the deterministic, explainable `scoreDiscovery`: keyword/profile overlap (title hits weigh far more than body hits), internship-by-title, freshness in HOURS (on a daily sweep everything is "recent", so days is too coarse), applicant count (6 applicants and 43,106 are not the same opportunity — both boards report it), Run-drivability, minus a promoted-listing penalty. `pickBestJobs` returns BOTH halves so everything left behind is reported and logged with its score + reasons; the panel shows the reasons per row. **Deliberately not an LLM call** — cheap, stable across runs, and auditable; AI ranking is a possible later addition through the existing `act.llm` seam.
- **Board-only applications are SKIPPED by default, with support explicitly DEFERRED.** LinkedIn Easy Apply / Handshake Quick apply expose no employer URL, so Run cannot drive them — queueing one only produces a red `board link` badge. `skipEasyApply` (default on, toggleable) drops them and the sweep NOTES how many, saying support is planned. Closed/archived postings are dropped too, and counted.
- **The REAL job link, not the board's (2026-07-30).** A `linkedin.com/jobs/view/<id>` url is useless to the Run pipeline, which drives Workday/Greenhouse/etc. So the JD pass RESOLVES each board find to the employer's application URL and rewrites BOTH `job.url` and `job.jobKey` (`boardUrl` keeps the origin) — which also means a LinkedIn find whose real link is a Workday req now keys identically to the tracker row written after applying, so `known` is re-checked post-rewrite and the job is dropped if already applied to. Extraction is **PASSIVE, never a click**: LinkedIn's apply button is deliberately NOT clicked because that can mark the posting "applied" on LinkedIn when it hasn't been. Ladder: `code#applyUrl` blob → an off-LinkedIn `a[href]` inside an apply container → an `externalApply`/`offsite` wrapper's `url=` param; the generic `scrapeJobPosting` does the same for Handshake's posting page (apply-LABELLED off-host anchors only — never links harvested from the description prose, which routinely contains unrelated company URLs). `applyKind` separates **"Easy Apply, so no employer link EXISTS"** from **"external but we couldn't extract it"** (a scraper gap worth fixing); either way the job still queues on its board url, is reported in a note, and the queue renders a red **`board link`** badge (`isBoardUrl`, LOCKSTEP web↔ext) saying Run can't drive it.
- **Logging is the debugging surface (`dlog`, all `[DISCOVER]`).** Per source: the URL opened, per-page card counts, sign-in state, then the filter arithmetic (already-applied / too old / unusable) and a numbered list of every kept job. Per record: char count and the apply-link outcome incl. `before → after` key rewrites. Ends with a per-source tally, a real-employer-link tally, and **every queued job's FINAL link + score + why** — so a sweep can be diagnosed from the console alone. `discoverProgress` logs AND emits, so the console and the on-page progress line tell one story.
- **Bounded, and NO SILENT CAPS.** `maxPerSource` 25 / `maxTotal` 60 / `maxJdOpens` 10 / `maxPages` 3 / `queueLimit` 10; whatever a cap drops is reported as a note. **`maxTotal` was silently INERT** until 2026-07-30: the web panel never sent it and `{...DEFAULTS, ...opts}` copies an `undefined` over the default, so `slice(0, undefined)` returned everything — the message forwarders now only pass keys the caller actually supplied. An **UNKNOWN posted date counts as FRESH** (unit-pinned): every source is already time-bounded upstream, so an unparseable date is a parse gap far more often than a stale job, and dropping it would hide real postings invisibly.
- **NEVER REQUIRE REAL FOCUS — EMULATE IT (operator 2026-07-30: "never require focus, figure it out").** The location resolve initially worked only in a FOREGROUND tab: identical trusted click, identical coordinates, panel opens when presented and never when hidden, because the reveal defers on rAF (paused) and timers (throttled to ~1Hz). Borrowing real focus was tried and REJECTED — a sweep must run unattended. The fix is the three levers cdp.js already has for this class of stall: `cdpInstallPageOverrides` (worker-timers escape background throttling; `Page.setBypassCSP` first, or a blocking CSP silently defeats it), `cdpWakePage` (`Page.setWebLifecycleState:"active"` unfreezes an outright-frozen tab, re-applied on every poll tick since a hidden tab can be re-frozen between reads), and **`cdpSetFocusEmulation`** (`Emulation.setFocusEmulationEnabled` — the page behaves as focused+active and keeps REPAINTING). Verified: "Denver, Colorado" and "Pittsburgh, Pennsylvania" both resolve with the tab unfocused, and the results come back genuinely Denver/Pittsburgh. None of it touches real window focus, and `cdpVisible`'s pacing sampler reads `chrome.tabs`, so adaptive pacing stays honest.
- **IDENTIFY A CONTROL POSITIVELY — never "the first input that isn't the one I know".** The worst bug of this build: Handshake's location panel is `display:none` until opened, so no location box is visible, and a "first non-keyword input" fallback returned the KEYWORD box. The resolver typed "Pittsburgh, Pennsylvania" into the job-search field, matched a job suggestion, clicked it, and reported `location-token-never-appeared` — a completely wrong ACTION disguised as a timing failure. (It also slipped an exclusion list, because the regex said `describe the job` and Handshake's placeholder is "Describe **a** job you want".) Both boards can be matched positively — LinkedIn by `componentkey="LocationTypeahead_TextEditor"`, Handshake by a placeholder naming a place (`city|state|zip|postal|location|where`) — so anything else returns null, which correctly means "the panel isn't open yet" and makes the caller open it. **Handshake takes any place its typeahead knows, INCLUDING a country** — verified: "United States" resolves and every result comes back US. An earlier build reported that Handshake "only takes a city, state or ZIP", quoting the box's own placeholder as evidence; that was WRONG and the operator corrected it. The failure was this very keyword-box bug (the text went into the job-search field, so of course nothing matched) and the tidy-sounding explanation outlived the bug that caused it. **Report what was observed, never a theory about a board's capabilities.**
- **A CONTROL THAT TOGGLES MUST NEVER BE RE-CLICKED BLIND.** The open loop clicked, waited a flat 500ms, checked once, and looped; the panel needs longer than that to mount, so attempt 2's click CLOSED what attempt 1 opened, alternating forever (`clicked yes, box NOT found` on all 8 attempts). Now: check whether it is ALREADY open before clicking, click at most once per round, then POLL. Same invariant as the Workday dropdown "toggle-shut" rule.
- **DIAGNOSTICS MUST TRAVEL IN THE RESULT, not just the SW log.** A sweep runs in an unfocused tab on a page nobody is watching, and `could-not-open-location-control` alone can't distinguish "no control found" from "clicked but nothing opened" from "opened but the box wasn't recognised". `resolveBoardLocation` returns a `diag` (attempts · control found + its label · clicked · box found · viewport · the filter-strip buttons it DID see · the suggestions it was offered · which it picked) and the note spells it out — which is what actually located all three bugs above. ⚠ Every failure path must carry it: one `return` omitted `diag` and the note then blamed a missing control that had in fact been found and clicked.
- **HIDDEN-TAB SAFE BY CONSTRUCTION (operator 2026-07-30: recon must work background as well as foreground).** Every wait and all pacing is SERVICE-WORKER wall clock, and the injected functions contain **no `setTimeout` at all** — Chrome throttles page timers to ~1Hz in a background tab but does not throttle `fetch`, so a batch of awaited fetches runs at full speed hidden. The location resolver is split into rect-returning STEPS for the same reason (each injection is instantaneous; the waits are all SW-side), and trusted CDP input needs no paint. Card discovery POLLS for the cards (`pollForCards`) instead of guessing a settle delay — Handshake's list can take 15s+ even in the foreground, and reporting "0 cards" for a page that was merely still rendering is the one thing recon must never do. The recon dump reports `readyState` + `hidden` + `visibilityState` alongside the counts so a zero is always interpretable.
