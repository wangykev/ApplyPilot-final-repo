# Onboarding walk (pre-form: JD → apply → login → verify; SW-driven, NEVER submits)
The stage BEFORE the fill walk: drive the active tab from a job-description page to a filled-in
application form. Port of the Playwright repo's `workday.py` (navigate_to_first_form_page →
handle_application_modal → handle_auth_screen → _handle_email_verification), on the CDP substrate,
hardened. **Live-verified visible + hidden** across Comcast, altasciences (wd1 — create → Gmail
verify → activate → re-sign-in → form), and Palo Alto Networks (wd5 — social-login chooser).
Orchestrator `runCdpOnboard(tabId, {credentials, gmailEnabled, startUrl})` (background.js);
handler `RUN_CDP_ONBOARD`; setup + caveats in `docs/gmail-setup.md`. **One-time setup required** (pinned
extension key + a Chrome-Extension OAuth client) — see that doc.

- **Reuses the CDP primitives, adds navigation.** New in cdp.js: `cdpNavigate` (`Page.navigate` — for the verify link + an optional start URL) + `cdpReload` (`Page.reload` — the soft-error refresh). Reads via `cdpOnboardScan` (self-contained; url/host/bodyText + apply/auth/form markers + `hasAuthEl`). Clicks via the walk's cover-check/auto-dismiss ladder (`cdpCoverCheck` + `cdpFindDismissControl` + `cdpClickAt`; `cdpCoverCheck` treats a Workday `click_filter` overlay as the click surface, not a blocker). Types via `focus → cdpSelectAllDelete → cdpInsertText → read-back`. NO input-lock (a takeover halt must leave the operator free to act). Detaches in `finally`.
- **Runs hidden-safe (adaptive pacing).** ALL click/type/transition pacing goes through the local `pace()` = `cdpAdaptiveDelay` (the fill's `act.delay` model): ~10× faster when the tab is VISIBLE/worker-timers-fast, FULL (throttle-immune) when hidden — every `pace()` site is gated by a read-back/poll/scan so a too-short fast wait only costs a retry. Transition waits (`settlePage`/`waitFor`) additionally `cdpWakePage()` each tick; `cdpInstallPageOverrides` (worker-timers) is installed at start. The ONE exception is the **5s post-activation settle** — a real server-commit wait (`cdpDelay(5000)`, never scaled): signing in the instant after the activate link leaves the account "pending verification" and re-triggers a 2nd email (the PANW double-cycle). First-run Gmail consent needs the interactive account picker; once the token's cached, subsequent runs are silent → hidden-friendly.
- **The decisions are PURE + unit-pinned (lib.js):** `pickApplyTarget` (chain `adventureButton → continueButton → applyManually`, first present wins; NEVER `useMyLastApplication`); `classifyAuthOutcome` (bodyText + form state → `verify`/`wrong_credentials`/`success`/`unknown`; success = a real form field present AND `!hasAuthEl`); `isWorkdaySoftError` (the "Something went wrong / please refresh" page — apology AND a refresh cue); **`looksLikeSso`** — an idp/saml/okta-style URL (POSITIVE evidence), or a sign-in button with no email/password field **but ONLY off a Workday host** (`isWorkdayHost`): **field-absence is NOT SSO evidence on Workday** (operator 2026-07-27, "Workday will never be SSO"). A still-RENDERING auth widget looks identical to a bare provider redirect — auth chrome up, fields not in the DOM yet — and live on Caterpillar wd5 in a BACKGROUND tab that produced a flat-wrong `sso` halt on an ordinary create-account page (the "Already have an account? Sign In" link satisfied `signInButtonPresent`). A real federated login LEAVES the Workday host, so the URL test still catches it; **`isAlreadyApplied` (2026-07-24)** — the `alreadyAppliedPage` marker (title is unreliable — a stale "Create Account" on Magna) or a "you've already applied" body-text fallback, checked at the initial scan + start of Stage 3 + after a successful sign-in + inside the auth loop so it never stalls on a form that will never appear. **It is no longer taken at its word (2026-07-28): the page is a LIE for started-but-unsubmitted applications** — see the recovery bullet below. `test/onboarding.test.js`.
- **ALREADY-APPLIED is VERIFIED, not believed (`handleAlreadyApplied`, 2026-07-28).** Workday shows "You've already applied for this job" for an application the candidate STARTED and never SUBMITTED, and the old code halted on it — abandoning a fillable application. The AUTHORITY is the candidate's own list, driven exactly as the operator does it by hand: **already-applied → "View My Applications" → expand the collapsed dropdown → find THIS job → read Submitted / Not Submitted → click it → the job-description page → "Continue Application" → page 1.** Decisions are PURE (`isMyApplicationsPage` / `applicationStatusOf` / `pickApplicationRow` / `reqIdFromUrl`, lib.js, unit-pinned); reads are `cdpReadApplicationsPage` / `cdpReadJobIdentity` (cdp.js) and clicks go through the existing `clickTarget` (re-measured cover-check) by way of `cdpTagClickableByText`/`cdpTagRowByHref`, which stamp `data-ap-click` on a TEXT-matched control — text anchoring is unavoidable here, no automation-id for this page is confirmed on any tenant. **`applicationStatusOf` tests the NEGATIVE first** ("Not Submitted" CONTAINS "Submitted"; a positive-first test abandons every fillable application — regression-pinned). **`pickApplicationRow` refuses ambiguity**: req-id (from the row href/text — titles truncate, req ids don't) → exact normalized title → containment committed ONLY on a single hit; 2+ matches ⇒ halt, because opening the wrong row would fill someone else's application. A row reading **submitted** ⇒ the original halt stands, now with evidence; **not-submitted** ⇒ recover; **no status word** ⇒ open it and let the posting decide (a "Continue Application" affordance is the positive proof it's still open). Before Continue it PROVES the requisition matches the one we're applying to. BOUNDED at 2 per run (one attempt can be spent on the list demanding a sign-in). It only ever REACHES a form — never fills, advances, or submits.

- **⚠ (historical, rounds 1–3) the PHANTOM "required" error (solarturbines page 5, HIDDEN replay).** Workday reports `Name` + `Date` as required-and-empty on a page where **everything is filled correctly** (operator-confirmed, eyes on the page). **What the `[FIELD-DIAG]` dump PROVED (2026-07-28):** the DOM holds the values (`name="Kevin Wang"`, date segments `7`/`28`/`2026`); **React's own `__reactProps$`/fiber hold them too** for every date segment; Workday's OWN widget renders `"current value is 7/28/2026"`; the fields carry `aria-invalid="true"` with an **inline per-field** error ("Error: The field Name is required…" — so it is NOT a stale page-level banner). ⇒ **The value is present in every layer we can read, and missing only from WORKDAY'S OWN FORM MODEL** — the layer above React that we cannot inspect. **Ruled OUT by live runs:** the blur race (round 1 — real focus+change+blur on all 4 inputs, then Save, still blocked, TWICE); a value revert (the pre-save `requiredBlankOnPage` re-verify never fires); React never getting the value (the date's React state has it); a stale/swallowed-click error (the errors are inline per-field). **Operator note kept for context:** by hand, a bare second Save cleared the Date error and a click into the Name box + Save cleared the rest — consistent with the confirmed cause (both give Workday a real interaction/re-validation). An automated re-submit tier built on that observation was tried and then REVERTED once the trusted re-write proved out live: re-submitting without re-writing is weaker, and `reclickNextWhenClean`'s refusal to re-click while error text is present is a guard worth keeping. **The remedy is the trusted re-write — the same failure mode is ALREADY documented in this codebase for the auth form (`cdpSetSyntheticInput`: *"the auth app likely doesn't register native-setter values in its own state, leaving the submit inert"*), synthetic input writes via the native setter, and this only ever happens on HIDDEN runs — the only ones using synthetic input. So the retry now re-writes the error-named fields with `cdpSetSyntheticInput(false)` (trusted `Input.*`, restored after) **and `skipIfCorrect:false`**. **If the page advances there, the mechanism is confirmed** and the fix becomes "use trusted input for these fields/this page" rather than paying for a retry; the log says so explicitly. **Round 2's bug, worth remembering:** `replayField` had its OWN skip-if-correct that ignored `budgets.skipIfCorrect`, so the first "forced" re-fill was a silent no-op (`already correct — left unchanged`) and cost a whole live run — now gated (`skipIfCorrect !== false`; `undefined` still skips so every existing caller is unchanged) and **pinned in both directions**. Also in place: (1) **`diagnoseRequiredErrorFields` → `cdpDiagnoseFieldCommit`** dumps `[FIELD-DIAG]` on EVERY required-error nav-timeout in BOTH walks, read-only, before any remediation touches the page — per input it prints the **DOM value vs REACT's own `__reactProps$`/fiber value**, the date spinbuttons' `aria-valuenow`, `aria-invalid`, whether it's focused, and whether the error node is rendered INSIDE that field's wrapper. Reading React's internals is the load-bearing part: DOM-vs-React divergence is exactly what a native-setter write that never notified React looks like, and it is invisible to every check we have (read-backs, the M40 audit and the page scan all read the DOM). The dump's own legend maps each combination to a hypothesis — **domValue set + react EMPTY** ⇒ React never got it; **domValue EMPTY** ⇒ it reverted after we verified it; **both set** ⇒ Workday's model disagrees with its own DOM; **no error inside any wrapper** ⇒ the error is page-level/stale and the Save click may have been swallowed. (2) A **mechanism-AGNOSTIC remedy** that covers several of those at once: force-re-actuate each error-named field with **`skipIfCorrect: false`** (a real clear+type even where the box already looks right), then re-save — this covers a revert, a stale React state, AND a Workday-PREFILLED field our skip-if-correct left untouched so its model never saw it completed (the live log's `1 already-correct` makes that a live candidate). Deterministic, approved values only, per-field verify still gates it, bounded 2/run. **If a run advances at `✓ … after force-re-filling`, that IS the answer — the value had to be re-WRITTEN, not just committed.**
- **BLUR COMMITS THE FIELD — Workday's PHANTOM "required" error (2026-07-28).** Workday validates a field on **blur**. `cdpSynthSetValue` fires keydown/input/change/keyup and nothing else, and the ONLY thing that blurs a synthetic-filled field is the NEXT synthetic click calling `el.focus()` — so the **LAST field filled on a page is still focused when Save & Continue is clicked, and its blur races the submit in the same tick.** Live on a HIDDEN solarturbines replay, page 5: every value physically correct and read-back verified (`0 FAILED`), and Save returned *"The field Name is required and must have a value"* + the same for Date. The operator's own workaround is the diagnosis — *"click into the field text box, then press next, and the error goes away"* — a focus/blur cycle with time to land. Two halves, both DETERMINISTIC (no AI, so they're allowed on the replay path): **preventive** — `clickPageNext` (the ONE method both walks advance through) calls `cdpCommitPendingEdits` to blur the focused editable + settle a beat before every Save; **curative** — on a nav-timeout with errors, `nudgePhantomRequired` focus→change→blurs each named field's inputs (`cdpNudgeFieldCommit` — a date composite walks its month/day/year spinbuttons; checkboxes/radios skipped, their commit is the click) and re-saves ONCE, bounded 2/run, as replay-walk tier and fill-walk **Tier 0.5** (before Tier 1, which would pointlessly re-actuate a verified value). Neither half ever touches a VALUE. The safety gate is the PURE, unit-pinned **`phantomRequiredTargets`** (lib.js): it fires only when EVERY error-named title maps to a field on the page **and** every one of them HOLDS a value — one genuinely-empty field, or one title it can't map, and it REFUSES, so a real validation block still halts. That direction is the pinned one: a false positive would re-save an incomplete page and bury a real gap under a retry.
- **DETECT THE LANDING — never assume a click went where it aimed (`classifyWorkdayPage`, lib.js, 2026-07-28; operator's standing rule).** Every caller used to test only for the ONE thing it wanted (auth fields, a form, the review marker), so any other landing read as "the thing I wanted didn't render" and halted naming the wrong cause. ONE pure classifier — `maintenance | soft-error | already-applied | my-applications | review | form | auth | job-description | blank | unknown` — ordered so transient/terminal states OUTRANK page shape (a soft-error page can carry leftover form chrome), and `form` requires fields AND no auth chrome (the same rule as `isPastAuth`). Used at every hop of the already-applied recovery and at the replay walk's empty-page halt, which now reports the page it actually found instead of reloading an already-applied/maintenance page three times. **When you add a redirect point, classify the landing and report it.**
- **APPLY→AUTH IS A BOUNDED LOOP, and a JD page is NOT an auth screen (2026-07-29).** `signInButtonPresent` is a TEXT match over every clickable, and a Workday POSTING carries "Sign In" in its own HEADER — so the job-description page satisfied Stage 3's `st.hasAuthEl || st.signInButtonPresent` condition, `doAuth` waited its full 30s budget for credential fields that were never coming, and the run halted **`auth-form-not-rendered`** while the state read `markers=[continueButton]` — the very button Stage 1 wanted to click. (Trigger: the posting came back EMPTY, `0 chars`, so Stage 1 found no Apply button and skipped; it then rendered during the auth wait, and nothing re-checked.) Fixes: **(1)** `onJobDescription(s)` — an apply-chain marker is POSITIVE evidence and beats the absence-based text match; it requires NO credential field, so a real auth screen can never match (**pinned both directions**). **(2)** Stages 1–3 now run inside a bounded `applyStage:` loop (`MAX_APPLY_ROUNDS = 2`), so discovering mid-flow that we're on a posting sends us back to Stage 1 instead of halting — `doAuth` returns `{backToApply:true}` and the caller re-runs the stage. **(3)** `onJobDescription` is in the `sign-in-form-render` wait's PREDICATE, so it exits the moment the button appears instead of burning the budget — the third instance of the **wait-predicate rule**: a wait must notice both that the GOAL arrived *and* that we're in the WRONG PLACE. Deliberately NOT fixed with a page reload (the operator's call: the empty page was the trigger, not the halt's cause).
- **Sign-in FIRST, create-account on wrong-creds.** The auth loop (`doAuth`, capped attempts): try sign-in as the stored credentials → classify → `success` land on form; `verify` → Gmail flow → re-sign-in; `wrong_credentials` → `doCreateAccount` (email/password/`verifyPassword`-or-2nd-password/consent-checkbox/`createAccountSubmitButton`; "already exists" → fall back to sign-in) → loop. Credentials are FIXED (`data/credentials.json` → storage — NON-dot, because Chrome won't serve a dotfile from an unpacked extension via `getURL`; same email reused per tenant — that's why sign-in-first works). The same Gmail `+alias` account works across all tenants.
- **Submit resilience + tenant variants.** Both submits (Sign In / Create Account) go through **`submitAndWait`**: click → wait for the outcome → **re-click if the form is still up** (up to 3 attempts) — the fallback for a raced/not-yet-enabled button (a scaled-fast click can land before Workday enables it). The FIRST submit click gets a **200ms** pre-click settle, then `submitAndWait` escalates a per-attempt outcome-timeout ladder. **Sign In is `[4000, 6000, 6000]` — NOT the `[500, 20000]` this doc claimed until 2026-08-11.** The 500ms first rung was removed on 2026-08-07 after it timed out on 3 of 3 sign-ins whose clicks had all WORKED: the form is still mounted at 500ms simply because Workday's auth POST hasn't committed, so `formStillUp` reads true and we re-click a submit already in flight — manufacturing a double submit whose blank-shell recovery costs a full page reload (the 8-9s). ⚠ **The double submit still happens at 4000ms** (live 2026-08-11: timed out at 4s, re-clicked, then `auth-unknown`), so the rung is a mitigation, not a cure — which is why the empty-shell RECOVERY has to work; see `isBlankAuthPage` / `blankAuthRefusal`.

- **✖ REFUTED — the sign-in form exposes NO in-flight signal, so the re-click can never be gated on one (MEASURED 2026-08-11; do not re-investigate).** Operator: *"the first click always works manually."* It does — the ladder infers "my click did not register" from the auth form still being MOUNTED, which is exactly what an IN-FLIGHT submit looks like, so it re-submits a form that is already working. `cdpOnboardScan.authBusy` existed to hunt for positive evidence of a no-op, with an explicit "measure before building on it". Measured, PAIRED, on one cold sign-in that re-clicked: <br> `idle (pre-click):  {busy:false, disabled:false, pwFilled:true, spinner:true, spinners:9, spinnersShown:9}` <br> `in-flight (4000ms): {busy:false, disabled:false, pwFilled:true, spinner:true, spinners:8, spinnersShown:8}` <br> **Every field is identical.** `disabled` and `aria-busy` are never set while Workday processes, and **9 spinner/progressbar nodes are already mounted AND laid out on the IDLE form** — so an earlier in-flight-only sample reading `spinner:true` was not evidence of anything. ⚠ **The baseline is what saved this:** gating the re-click on `spinner` would have suppressed it ALWAYS, including for genuinely swallowed clicks — a strictly worse bug, invisible in testing. **Consequence:** no ladder tuning can separate a swallowed click from a slow one; the only levers are TIME (longer rung = fewer false re-clicks, slower genuine recovery) and making the empty-shell RECOVERY good. A double submit is also not automatically fatal — live it re-clicked and still reported `sign-in outcome: success`. Workday's own transparent **`click_filter`** overlay is treated as the click surface (`cdpCoverCheck`), not a blocker. **`submitAndWait` first dismisses Chrome's password-manager overlay (2026-07-23):** the autofill dropdown is BROWSER chrome painted above the page — `cdpCoverCheck`/`elementFromPoint` can't see it, so a coordinate click on the button below it silently MISSES and the walk halts `auth-unknown`. An **existing-but-unverified account** (sign-in → `verify` showing a "Resend Account Verification" button, `cdpResendVerifyRect`) gets Resend CLICKED before polling Gmail — the original email is stale/expired. This makes the flow idempotent across re-runs of the same `+alias`.

- **WAIT-PREDICATE AUDIT (2026-07-27) — two standing rules for any new wait.** Three bugs in one day shared a shape: *a wait polls for one specific thing and misses that the goal was already reached, or that it can never be reached.* All 10 onboarding `waitFor` sites were audited. **(1) Accept the GOAL STATE:** a wait for sign-in fields must also accept `isPastAuth` (the sign-in may have landed mid-wait) — fixed in `sign-in-form-render`, `email-sign-in-form`, `post-blank-reload`, and `switchAuthView`'s view wait (a signed-in page can never "switch views"); the other six already accepted it via `classifyAuthOutcome`/`formFieldCount > 0`. **(2) Bail on a TERMINAL state:** `waitFor` itself now exits early (with a log + a `terminal` field) on **already-applied** or **maintenance** — every predicate waits for a page to BECOME something, and on those pages it never will, so an already-applied posting used to burn 20s + 45s + 12s in sequence before the flow noticed a state it detects instantly. Also found: `doAuth`'s loop top never checked `isAlreadyApplied`, so an already-applied page reached inside the loop halted `auth-form-not-rendered` — its shape (no form, no auth chrome, no fields) is exactly what that halt tests for. `cdpWaitNextPage` was audited and left alone: it already guards maintenance + session-death first; it does NOT early-exit a soft error (costs one wasted timeout, then the caller's own check catches it) — deliberate, it's the most load-bearing wait in the system.
- **Every auth WAIT also accepts "we're already past auth" (2026-07-27).** The `sign-in-form-render` / `email-sign-in-form` / post-blank-reload waits polled ONLY for sign-in fields, so a sign-in that SUCCEEDED mid-wait went unnoticed: live, the wait timed out reporting `formFields=14 · hasAuthEl=false · markers=[applyFlowPage,formField]` — the application form — and the flow halted `auth-form-not-rendered` **on its own success**. `isPastAuth(s)` is now in each predicate, each wait is followed by an `isPastAuth ⇒ continue` (the loop top returns `reached_form`), and the `auth-form-not-rendered` halt re-checks it first. NOTE the budget was NOT the problem — the form appeared inside the 8s window; the predicate simply wasn't looking for it.
- **The EMPTY shell after a sign-in submit → RELOAD, don't halt (2026-07-27).** Live on cat.wd5/solarturbines: the sign-in submit returned a page with `readyState=complete` and NOTHING on it — no form fields, no auth chrome, no markers, body text just the cookie boilerplate, while the title still read "Create Account". `classifyAuthOutcome` can only say `unknown`, so the run halted `auth-unknown` and handed the operator a recoverable hiccup ("the solution is to just refresh the page"). `isBlankAuthPage(state)` (lib.js, PURE, unit-pinned) detects it and `doAuth` RELOADS + retries, bounded at 2 (`MAX_BLANK_RELOADS`), then halts `blank-page-after-signin` with an actionable message. **STRICT by design** — it authorizes a page reload, so it requires a FULLY LOADED document (never fires mid-navigation, where absence proves nothing) with EVERY actionable marker absent (any field / auth control / apply button / already-applied marker / real body text ⇒ not blank). A scan without `readyState` fails closed. **Correlation worth knowing:** it followed the fast RE-CLICK of Sign In — the first click was in flight, not swallowed. That lever has now been pulled twice (500ms → 4000ms, 2026-08-07) and the double submit STILL occurs, so lengthening it further is not the answer; the recovery is. **⚠ THE CAP WAS THE BUG (2026-08-11).** A live run halted `auth-unknown` on a page where every structural gate passed (`readyState complete · formFields 0 · hasAuthEl false · markers [none]`) — the cause was `BLANK_PAGE_BOILERPLATE_MAX`, then **700**, while cat.wd5's cookie notice ALONE measures **574 chars** (a shell lands ~650-750; a real content page measures 2306). The cap sat inside the noise band, so the reload this detector exists to authorize was refused on exactly the page it was written for. Raised to **1500**, regression-pinned. And because that cause had to be found by ELIMINATING every other gate — the body-text length being the one input the halt never printed — **`blankAuthRefusal(state)` now names the refusing gate in the halt log**. Same standing lesson as the auth-render bug: when a decision refuses, log WHICH input refused.
- **HIDDEN-TAB RENDER BUDGETS + SELF-DIAGNOSING WAITS (2026-07-27).** A backgrounded tab paints far slower — live on Caterpillar wd5 the auth widget needed **>20s** after "Apply Manually" (that wait timed out at its full 20s, then the very next scan saw the auth screen), and the follow-on `sign-in-form-render` wait was a flat **8s**. A too-short budget didn't just cost time: it made the flow conclude the fields would never arrive and halt on the WRONG reason (the false `sso` above). So both auth-render waits go through `renderBudget(visibleMs, hiddenMs)` (`cdpVisible`-gated — VISIBLE keeps the tuned live-verified values, HIDDEN gets 45s/30s), and a genuinely fieldless auth screen now halts `auth-form-not-rendered` (self-explaining: "run it in the foreground") instead of blaming SSO. **Diagnostics (the bug was unactionable because every failure printed the same line):** `scan()` no longer swallows read errors into `null` — it counts OK/failed reads and keeps the last error; a `waitFor` timeout logs those counts, the tab's REAL visibility, and `describeState(last)` (url · title · **readyState** · formFields · email/password/signInWithEmail/signInButtonText/hasAuthEl · the present markers); and every `needs_operator` halt in the auth stage goes through `haltNeedsOperator`, which LOGS the reason + that state (they were silent returns, so the SW console just ended at "detached").
- **Safety / halts.** NEVER submits; never clicks an affirmative consent-popup control; refuses SSO (`sso` halt → manual login then re-run — URL-evidenced only, see `looksLikeSso`). Every human-needed stop returns `needs_operator` + a self-explaining `stopped`/`detail` (SSO / no-credentials / verification-required-gmail-off / verification-email-not-found / verify-link-invalid / apply-*-blocked / auth-unknown). **Contract:** `ok:false` ⇒ a CRASH only (attach/navigate/exception); a needs-operator outcome is `ok:true` + `needs_operator`. **Verify links MAY be session-bound** (operator flag) — the flow navigates the tab to the fetched link and halts `verify-link-invalid` if the tenant rejects it; confirm end-to-end per tenant before trusting auto-verify.
- **Hand-off.** By default onboarding STOPS on the form (`reached_form`) — it does NOT auto-run the fill walk (which ADVANCES a live application). The `RUN_CDP_ONBOARD` handler chains into `runCdpWalk` ONLY when `onboardConfig.continueToWalk === true` (popup toggle, OFF by default; keep off until on a DISPOSABLE application). Popup: **Onboarding** section (Load credentials / Start URL / Gmail toggle + Connect-test / continue-to-walk toggle / Start).
- **WHICH ACCOUNT a run signed in as is RECORDED per application (2026-07-26).** Workday accounts are per-TENANT, so weeks later "what did I sign in as here?" is a real question, and after a create-account run the tracker row is the only record the account EXISTS. `recordRunLogin({email,url,tenant,created,verified})` writes `chrome.storage.local.lastRunLogin` the moment a run reaches the form — at EVERY onboarding call site (website Run, website Submit, popup `RUN_CDP_ONBOARD`) — and the handlers RETURN it so the website records what the extension ACTUALLY used (not its own possibly-unsynced copy). `getRunLoginFor(bundleUrl)` attaches it to `reportApplication`'s payload **MATCH-GATED**: exact `job_key`, else same tenant, else `null` — a stale record from another tenant must never be reported as this application's account (**no login beats a wrong one**), and an empty email is also `null` (a hand-signed-in run has nothing truthful to record). Backend columns + the tracker-detail "Signed in as" line: `WEBSITE.md` (migration `0011`). The PASSWORD is never copied per row — it lives once on `credentials_json`.
