# ApplyPilot Chrome Extension

Docs: `docs/dom-patterns.md` (the observed-DOM rulebook) · `docs/progress-log.md` (full milestone history — append new milestone entries there).

## What this is

A Manifest V3 Chrome extension that automates Workday job applications from a stored profile. From-scratch rewrite of a Python + Playwright tool of the same name; the Python repo lives separately and is a **design reference, not code to port** — it documents what the system should do; this repo builds it for the runtime that will ship. The shape is a **fill → review → submit** pipeline: the engine fills a page and produces a per-field review summary, a human reviews/edits it, and a later pass replays the approved values. All three stages are built; the SUBMIT stage is live-verified in **SIMULATE mode** (it runs the full replay + precondition gate and logs "would click submit" — no real click yet; going live is one flag flip behind an eyes-on, disposable-app gate).

## Architecture & invariants

- Manifest V3; host permissions `*://*.myworkdayjobs.com/*`.
- **Active-tab injection — NOT a content script, NOT a background tab.** `background.js` (service worker) receives a `RUN_FILL` message from the popup and uses `chrome.scripting.executeScript` to inject `fillEngine` into the active tab (frame 0). *Why:* the operator is logged in and on the form themselves, so injecting into the active tab fills the page they're looking at. Content-script files and background-tab/multi-page automation were deliberately deferred — not needed for active-tab fill.
- **Profile + defaults + jobContext live in `chrome.storage.local`** — the permanent website→extension handoff contract. The engine ALWAYS reads them from storage (today the popup's "Load default profile" seeds `profile` from `data/profile.json` and `defaults` from `data/application_defaults.json`; `jobContext.company` is set via a popup field; later a website will write them). The engine is agnostic to how they got there.
- **"Engine computes / service worker does I/O."** The injected `fillEngine` is self-contained (closes over nothing from the SW), reads/writes the page DOM, and RETURNS results — it never touches `chrome.storage`. `background.js` does all storage I/O (e.g. persisting the review summary). Keep this boundary.
- **Pipeline shape:** fill (engine, per page) → review (the `reviewSummary` + `summary.html` viewer/editor, human edits) → submit (replay approved values; not built).
- **UI:** `popup.html`/`popup.js` — profile/resume/LLM config + the fill, recon, and walk buttons (see CDP section → Entry points). `summary.html`/`summary.js` — the review-summary viewer/editor. `[ApplyPilot]` logs land in the **service-worker** console (see Working principles → three consoles).

## Workday DOM model

See `docs/dom-patterns.md` for the full, dated rulebook (every observed tenant + refutations). Short version:
- Every form field sits in a `<div data-automation-id="formField-*">` wrapper.
- `classifyField` derives the widget type from wrapper descendants, first match wins: **hierarchical `source` → typeahead (`data-uxi-widget-type="multiselect"`) → radio (`input[type=radio]`) → dropdown (`button[aria-haspopup="listbox"]`) → checkbox → text → unknown**.
- **Rules come from observed DOM, not the Python spec.** Patterns the spec assumed do NOT hold on observed pages (e.g. `role="combobox"`, `role="radiogroup"` don't fire on Comcast). When code and doc disagree, fix one — don't let them drift.

## React fill technique

Workday is React-based: `input.value = "x"` updates the DOM but not React's internal state, so the value reverts on submit. The working pattern (verified on Comcast text fields; needed for any controlled input):
1. native setter: `Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype, 'value').set`
2. `nativeSetter.call(input, value)`
3. dispatch `new Event('input', { bubbles: true })`
4. dispatch `new Event('change', { bubbles: true })`

## Interaction patterns (the shared helpers)

Primitives proven against real Workday pages, now the shared helpers inside `fillEngine` (`background.js`). Reuse them — don't reinvent.

- **`robustClick` — the click primitive.** Three-strategy ladder: (1) pointer-event sequence (`pointerdown→mousedown→pointerup→mouseup→click`, `clientX/Y` from the bounding rect — closest analog to a real click), (2) native `el.click()`, (3) bare `MouseEvent('click')`. On Comcast the pointer sequence has succeeded on every widget; the fallbacks are kept because portaled-listbox/overlay layers can mask synthetic clicks on other tenants. Use it for any non-text-input interaction.
- **Typeahead is open-before-find.** The searchBox `<input>` isn't reachable until the widget opens (container carries `data-automation-hiddensearch="true"`). Click the opener first, then `waitFor` `input[data-automation-id="searchBox"]` scoped to the wrapper. Opener ladder: `[data-automation-id="multiselectInputContainer"]` → `[data-uxi-widget-type="selectinput"]` → first `<input>` → wrapper.
- **Clear before typing.** Set the search input to `""` (native setter + input event), wait briefly, then type — avoids residual-text contamination on re-fill.
- **Settle-poll the filter, don't scrape on a fixed delay.** Live-filtering typeaheads race a fixed `setTimeout` (we saw option counts flip 21↔1 with wrong matches). Poll the enabled-option count ~120ms and accept only after **two consecutive equal, non-zero reads**, with a timeout fallback to the latest read.
- **Sequential cleanup — don't over-engineer per-field close.** Moving to the next field blurs the prior widget and dismisses its listbox for free. We burned time on explicit Escape/click-outside closes before realizing the sequence handles teardown. Per-field handlers focus on open+select; only the last field could leave a listbox open (cosmetic).
- **Radios: click the label, group by `name`.** Inputs are CSS-clipped; the `<label for="<id>">` is the styled click target (native label-activation flips `checked` + fires the change event React listens for). Group by shared `name` (not a `role="radiogroup"` wrapper, which Comcast omits). Verify via `input.checked`.
- **Options are portaled to the document root** (outside the `formField-*` subtree). **But a bare page-wide `[role="option"]` scrape is contaminated** — scope dropdown scrapes to the field's own listbox (see DOM lessons → chip contamination + aria-controls scoping). Filter `aria-disabled="true"` (the "Select One" placeholder).
- **Always verify state, not just click outcome.** `robustClick` returning a strategy means an event fired, not that the page updated. Re-read observable state after a delay: radios → `input.checked`; dropdowns → trigger text; typeaheads/source → the `selectedItem` chip / `multiselectlistitem` selected-state. Synthetic clicks have no-op'd silently.

## Choice-widget handlers & hard-won DOM lessons

These cost multiple rounds; full per-tenant detail is in `docs/dom-patterns.md`. The load-bearing whys:

- **`source` ("How did you hear about us?") has three tenant shapes**, all handled by `fillSource` (discover-and-trace): Cambium = button+listbox **expand-walk** (no searchBox); Comcast = typeahead; **US Bank = searchBox that filters on ENTER, not live**, whose result leaves are `<div data-automation-id="promptOption" data-automation-label="…">` — **NOT `role="option"`** (that role is on a sibling `menuItem`), and whose searchBox `aria-controls` points at a `promptAriaInstruction` node (the wrong target). So: type → full Enter → race-safe wait for `promptOption`s → match on `data-automation-label` → click → **commit-gated** via the enclosing `multiselectlistitem` selected-state (so no false "filled").
- **Dropdown option contamination — and why visibility filtering is a DEAD END.** A page-wide `[role="option"]` scrape pulled in two *genuinely-visible* contaminants: (1) **selected-item CHIPS** — a filled multiselect/source renders its selected value as `<ul role="listbox" data-automation-id="selectedItemList"><li role="option" data-automation-id="selectedItem">…</li></ul>`, i.e. **the chips carry `role="option"` markup**, so "LinkedIn"/"(+1)" showed up as options inside every dropdown; and (2) **a prior dropdown's listbox stays open** (filling State, Country's `ctny0` was still mounted, so State listed countries). **Visibility filtering was tried TWICE and confirmed a dead end — do not retry it**: both contaminants are genuinely `visible:true` (the chips are shown; the prior listbox is still open), so a visibility filter can never remove them. **Fix:** scope the scrape to the trigger's own `aria-controls` listbox (verified per widget: `ctny0`→countries, `ctny1`→states, `ctny2`→phone-types — unlike `source`, here aria-controls resolves to the real options container). `settlePoll` also excludes `selectedItemList` chips.
- **`is_required` detection varies by tenant.** Workday marks required fields with one of: `<abbr title="required">`, a **bare `<abbr>*</abbr>`** (asterisk as content, no title — US Bank dropdowns), `aria-required="true"`, or a label/legend whose visible text **ends with `*`**. Detect all of them (safe over-flag direction). Accuracy matters: a required field reading *false* is the dangerous direction — it hides an unfilled required field, and a required field the engine can't fill will block page advancement.

## Matching strategy

How a choice widget picks an option. Architectural decision, with rationale:
- **Value is an ordered candidate list, most-specific first**, supplied by the profile (`resolve()` coerces per widget type; an array passes through as a ready-made tiered list). The handler tries candidates in order.
- **Match ladder (per candidate, stop at first hit):** (1) **Exact** after `normalize()`; (2) **Containment — AMBIGUITY-SAFE** — `startsWith` then `includes`, but committed ONLY when **exactly one** option contains the candidate; a candidate contained in **2+ options is NOT a confident match** (e.g. "United States" is in both "…of America" and "…Virgin Islands") → skip it, never first-wins → escalate; (3) **Fuzzy ≥ 90** Levenshtein — **TYPO TOLERANCE ONLY**; (4) **Escalate** → `needs_review` rather than guess.
- **Why ambiguity-safe containment:** a first-wins `findIndex` silently committed whichever ambiguous option the tenant listed first (a wrong value — the worst failure for an accuracy tool). The exact tier still protects the case where the candidate IS a complete option (it runs first). Unambiguous containment is unchanged — the cert tree-leaf "Training Instructor - AEVO" → its single suffixed leaf still fills (`directed-containment`); "Bachelor" → "Bachelors" still fills. **Fix lives in `matchCandidates` (lib.js + the inline `fillEngine` copy in `background.js` — LOCKSTEP).**
- **Why not low-threshold fuzzy:** a 60% bar matches near-gibberish and silently selects a WRONG value, corrupting the application — the worst failure for an accuracy tool, worse than leaving a field unfilled. Fuzzy is typo-tolerance at 90+, not a general matcher.
- **`normalize()`** lowercases, strips a trailing `(+digits)`, collapses whitespace — lets "United States of America" exact-match the rendered "United States of America (+1)" with no fuzzy step. A tiered profile array (e.g. `["United States of America (+1)", "United States"]`) makes the exact-normalized hit land at **high** confidence instead of containment (medium).
- **needs-review / fuzzy connection:** a fuzzy/no match is not a confident answer — it's exactly the category that belongs in the human-review pile.
- **Parked (opt-in per field, never global):** dial-code-suffix matching ("any `(+1)` is acceptable for a US phone"). Global would silently accept a wrong country whose dial code happened to match.

## AI feature — multi-provider LLM (AI-0…AI-4 built)

Not-in-JSON questions (free-text/essays, unmapped choice fields, yes/no screening) leave REQUIRED fields empty → block Save & Continue → need an LLM. Built behind ONE provider-agnostic seam; **every AI fill is under the safety contract — guess + fill + FLAG `needs_review`, never silent trust — and the human review gate is the safety.**

- **The seam (`act.llm`, AI-0).** `llm.js` is the ONLY provider-aware code: `callLLM({provider, model, apiKey, system, user, maxTokens})` → normalized `{ok, text} | {ok:false, error}`, **NEVER throws** (Anthropic / Gemini / OpenAI builders+parsers; adding a provider = one entry). `LLM_MODELS` = curated per-provider model lists feeding the popup **dropdown** (default = the FIRST entry, single source of truth — **`gemini-3.1-flash-lite`** leads; a stale hardcoded model was the 429 lesson). `makeCdpActuation(llmConfig)` exposes `act.llm` (the only I/O method on `act`) + `act.aiEnabled` — both enforce the opt-in toggle (OFF ⇒ no provider call, no spend). The brain (fill-driver.js) builds the prompt + owns the decision, so it stays Node-testable with a fake `act.llm`. Popup config (provider/model/key + toggle + Test-connection); `manifest.json` host_permissions for the 3 hosts.
- **AI-1 — screening-question dropdowns (`aiFillField`, fill-driver.js).** A gated dispatch post-pass fires when `act.aiEnabled && f.isRequired && aiEligible(f) && producedNothing(record)` (an unmapped dropdown / genuine no-match). **ALWAYS-GUESS** — no UNKNOWN gate, because these are REQUIRED fields and a blank HALTS the walk: open → read the live options → `act.llm` with the profile + question + exact options → the model CHOOSES one + a SHORT justification that NAMES its basis (a positive profile fact vs reasoning-from-ABSENCE) + a confidence (High/Medium/Low). The choice is a **CANDIDATE that must clear the match ladder** vs the live options (never blind-commit) → text-keyed commit + read-back + persistence re-read. ALWAYS `filled_review`. `parseAiReply` tolerates ```-fenced / embedded JSON + a non-JSON fallback.
- **Safety / eligibility (HARD, unit-pinned).** AI-fill an unmapped/unmatched **dropdown / text / typeahead** — **but ONLY when the field is REQUIRED** (operator rule). An OPTIONAL unmapped dropdown/text/typeahead fills **deterministically only** and is left **BLANK** on a miss — a blank optional doesn't block Save & Continue, so there's no reason to spend an LLM call guessing it (INCLUDING optional EEO, incl. cascade-revealed Local-Name fields). The gate is `f.isRequired && aiEligible(f)` on `drivePageFill`'s INFER branch; `aiEligible` itself is a detector. The two value-CANONICALIZE paths (`aiCanonicalizeField` for a STATED dropdown value; the inline typeahead AI that only fires on a `resolve()`-produced candidate) are NOT gated — they operate on a value the user PROVIDED, not a guess, so they run for required OR optional. NEVER (regardless of required): `file_upload` and `checkbox`. A REQUIRED **radio** the deterministic pass can't answer now gets an AI guess via its OWN post-pass (`aiFillRadio` — NOT through `aiEligible`, mirroring the typeahead pass): infer from the profile → the pick clears the match ladder vs the live labels → commit via `fillRadioCdp` → ALWAYS `filled_review`, flagged HARD, never blank-blocking. This INCLUDES `candidateIsPreviousWorker` when its employer-match path is UNEVALUABLE (no company set + no known employer named) — the **safety reversal**: AI-guess to REACH review (force-flagged `ai-choice-sensitive` → LEGALLY-LOADED; a low-confidence guess auto-escalates to super-hard in the viewer) rather than leave a truthfulness-adjacent required field blank. GATED on `record.resolved == null` so a decided-but-uncommitted employer-match answer (e.g. a matched "Yes") is NEVER overridden by a contradictory guess. AI OFF / OPTIONAL radio ⇒ stays blank (unit-pinned). **EEO/protected (gender/race/ethnicity/veteran/disability/sexual-orientation) is NO LONGER excluded for REQUIRED fields — the operator RETRACTED that rule: a REQUIRED EEO field fills via the SAME AI inference as any required field, then gets the loud `ai-eeo-guess` "AI-GUESSED DEMOGRAPHIC — VERIFY" review badge (re-tagged at the call site; `isEeoField` is a detector, not a blocker). An OPTIONAL EEO field is left BLANK (the optional gate above — uniform). A STATED demographic still fills deterministically — the AI never overrides a value you provided.** Toggle OFF ⇒ `act.llm` never called. `legallyLoaded(label)` (widened to catch "over the age of 18") → `ai-choice-sensitive`.
- **The no-commit dismissal (`closeAndVerifyBlank`).** The UNKNOWN/no-match path must leave the field BLANK — and **blank is VALUE-based** (`triggerText` stayed on the opening placeholder), NOT the listbox state: a STRAY commits a value (which ALSO closes the list), so the value-check is the real property; a genuinely CHANGED value is surfaced (`*-stray`), never a false "blank, please answer." (An `ariaExpanded` hard-gate + a reopen-toggle once manufactured a false stray on a slow-closing list — both removed.) This is the SOLE guard on the no-commit path (the M40 audit only re-reads `filled`/`filled_review`, never a blank field). Reused by the recon (`reconDropdownDump`).
- **The review gate bites (two operator requirements).** `flag` is persisted in the bundle; `deriveConfidence` surfaces the AI's self-reported confidence (`confidence_source:"ai_inference"`); the viewer (`summary.js`) renders **`ai-choice-sensitive` answers FIRST with a red "⚠ LEGALLY-LOADED — VERIFY" badge — prominence off the FLAG, never confidence** (a high-confidence reasoning-from-absence answer, e.g. criminal→"No", must NOT be the easiest to scroll past) + the AI-INFERRED badge + the justification (which names its basis). The super-hard tier (`ai-closest-forced` + low-confidence AI) renders loudest, FIRST. M40 audit re-reads AI fills.
- **AI prompts pass the STATED answer (the candidates), NOT the whole profile**, when one exists (`statedAnswerBlock`) — saves tokens + matches a typo ("Otherrr"→"Other") instead of inferring an unrelated profile fact; falls back to the profile only when there is no stated answer (e.g. EEO).
- **Recon harness** (`reconDropdownDump` + `RUN_CDP_QUESTIONS_RECON` + `cdp-questions-recon`): read-only dump of a screening page's dropdowns (verbatim labels + options + a verified-blank clean-close) — the new-tenant probe before relying on the fill path.

AI-2 (essays — the required-text INFER branch) and the AI-3 EEO corner (`aiInferEeoField`, kept only for the mapped-but-empty REQUIRED EEO dropdown) are built, live-verify pending. ## Answer buckets (website-driven; Profile v2)

The website (`WEBSITE.md`) owns a `buckets_json` store synced via `AP_SYNC_PROFILE`. A **bucket** = one
canonical answer + the question wordings that map to it. The extension consults them in `drivePageFill`
for any UNMAPPED field the deterministic pass left empty, **before** the AI post-pass:
- `buildBucketIndex(buckets)` builds normalized-wording → bucket (`apMatch.normalizeLabel`, LOCKSTEP with
  the website's `normalizeQuestion`). **Exact-normalized match only — no fuzzy** (the AI fallback covers
  misses; a fuzzy tier would only add silent-wrong-match risk).
- `fillFromBucket`: **Mode A** (`profile_path`) resolves the bound profile value; **Mode B** uses the
  bucket's own `value`. Either way it's a CANDIDATE through the SAME match ladder vs the LIVE options —
  never a blind commit; a no-match falls through to AI/blank. A real commit is flagged `bucket`
  (a "remembered"-style provenance, NOT an `ai-*` flag). Gated `producedNothing(record) && !mappedPath`
  (a mapped-but-no-match field goes to CANONICALIZE instead). Runs for REQUIRED **and** OPTIONAL fields.
- The SW loads `buckets` from `chrome.storage.local` and hands them into `drivePageFill` (engine computes /
  SW does I/O). Unit-pinned in `test/fill-driver.test.js` (fake bucket: Mode A/B, match-ladder gate,
  runs-before-AI, `buildBucketIndex` normalization). **Supersedes** the earlier `answerBank` sketch.
- Not-yet-wired: date/textarea bucket **filling** (labels/wordings persist; the tier fills
  text/dropdown/radio/typeahead/checkbox). `normalize`-style lockstep dup: `normalizeLabel` (lib.js) ↔
  `normalizeQuestion` (web `lib/buckets.ts`).

## Employer match — "previously employed here?" (safety-critical)

`candidateIsPreviousWorker` sits next to a **truthfulness certification**, and selecting "Yes" unfurls follow-up fields — so a wrong "Yes" is a false legal statement. `decidePreviousWorker(company, questionText, employers)`:
- **clean miss** (no known employer matches) → fill **"No"**, no review (confident non-membership).
- **partial overlap** with the application company → fill **"No" + review** (name overlap may be the same employer).
- **exact company match OR a known employer named in the question text** → fill **"Yes" + review**.
- **unevaluable** (no company set / list unconfigured / `[]`) → **blank + review** — no blind guess.
- **NEVER auto-"Yes" without a review flag.** *Why:* this field is adjacent to a truthfulness certification and a "Yes" unfurls follow-up questions, so a wrong positive is a false legal statement — every "Yes" (and every uncertain "No") gets a mandatory human check, never a silent auto-answer.
- **Question-text scan:** these questions name the entities that count (affiliates/subsidiaries/predecessors — "Elavon, U.S. Bancorp Investments, Union Bank"; "Ken Garff") which the bare `jobContext.company` misses. Scan the question label for each known employer via a **contiguous whole-word token-sequence** match, gated by a distinctiveness check (multi-word, or a lone word ≥5 chars not in `GENERIC_SINGLE`) so a short/common entry ("Bank") can't false-match boilerplate. Works even with `jobContext.company` unset (adds a "no company to corroborate" note). It reads the user's KNOWN employers out of the question — it does NOT extract company names from prose (no LLM).
- **`employment_history_companies` = industry employers ONLY** (companies you were formally employed by; excludes academic/lab/club affiliations). Its completeness is what makes the auto-"No" safe. `["none"]` = "never formally employed" → confident "No"; `[]` = unfilled → flags every such question for review.

## Review summary (the fill → review → submit contract)

Stage 1 of the pipeline. On a **fully-completed** run the engine builds a `reviewSummary` bundle and RETURNS it; `background.js` writes it to `chrome.storage.local` — **only on completion** (a crashed/aborted run writes nothing; no partials).
- **Envelope:** `schema_version` (**"1.1"**; viewer tolerates 1.0), `page` (the stable MERGE key — `cdpPageKey` = pathname|field-set on CDP, the field-set key on the page engine; "accumulated (N pages)" once merged), `page_number`/`page_label` (display only), `url`, `tenant`, `captured_at`, `total`, `counts` (by fill_status), `by_type`, `needs_review_count`, `entries[]` (every field, page order). The viewer may also write an `approval` roll-up (see below).
- **Per-field entry:** `field_id` (**PAGE-QUALIFIED** `<page_key>::formField-<name>` — globally unique in the accumulated bundle, on BOTH paths), `page` (= the merge key, NOT the human label), `page_number` (the walk's 1..N ordinal — display order; null = single-page) + `page_label` (friendly caption), `field_index`, `question_label`, `widget_type`, `canonical_field`, `is_required`, `current_value` (the value actually filled — selected option text for choice widgets; only ever a live page value), `original_ai_value` (the bot's pick at write time, never changed by edits), `is_edited`, `edit_kind` (`override` / `filled_blank` / `cleared` / `null` — provenance for the later replay), `is_approved` + `approved_at` (human sign-off), `confidence` (high/medium/low/none) + `confidence_source` (the tier), `needs_review` + `needs_review_reason`, `fill_status` (filled/not_filled/skipped/error) + `fill_error`, `detail`, `match_tier`, `options` (full list, plain dropdowns), `captured_options` (the partial filtered set, typeaheads), `tree_structure` (cert/source tree-AI: chosen category + leaves), `character_count` (reserved).
- **Required-field escalation:** a required field left unfilled surfaces in review (highest-value review item — and, multi-page, it blocks page advancement).
- **Page keying — merge key vs display.** `page` is a STABLE merge key (field-SET, not the shared `applyFlowPage` container id — the M31 lesson); `accumulateBundle` merges on it (keeps OTHER pages + viewer edits verbatim). The viewer ORDERS pages by `page_number` and CAPTIONS by `page_label` (never the raw composite key — `cleanPageName` collapses it to the path tail). Both paths clear once at walk start + ACCUMULATE write-per-page; the SW stamps `page_number` per page (the engine doesn't know the ordinal).
- **The summary is the page's SOURCE OF TRUTH:** `sweepAlreadyFilled` (the LAST pass in `drivePageFill`) flips any `skipped` record whose field HOLDS a live value to `already-filled` (needs_review; `already-filled-match` unflagged when it equals the profile value; both AUDIT-EXCLUDED — never re-actuated); unknown/generic sections surface with current values + an addable stub carrying the DOM-detected `section_field_shape` (an EMPTY unknown section is revealed-by-add ONCE per bundle-lifetime); pre-advance `reconPageTruth` re-syncs deleted/index-shifted rows to the live page before every remediation re-click; AI-4's synthetic rows are filtered from the bundle. `current_value` renders for ANY status, so a needs_review kept-original shows the real field value.
- **Viewer/editor** (`summary.html`/`summary.js` + the PURE, requireable `summary-lib.js` — `editKindOf`/`tokenFor`/`checkedOf`/`effectiveValue`/`approvalEnvelope`, tested in `test/summary.test.js`): NEEDS REVIEW first, then ALL FIELDS. **Every widget is editable** — plain dropdown/radio → `<select>` from `options`; typeahead/source/tree → a type-to-filter combobox (`position:fixed`) over `options`/`captured_options`/`tree_structure.leaves` + a partial-note; text/date/textarea/checkbox editable; radio without captured options degrades to a text box + note. Edits write back into the SAME record (`current_value`=pick, `original_ai_value` preserved, `is_edited`/`edit_kind` set), persisted, updated in place (no re-render → no scroll jump). Approve-by-section; required-EMPTY fields refuse approval (with a note); a checked "I currently work here" hides that entry's To row (a FLAGGED endDate stays visible); a gray PRE-POPULATED badge marks `already-filled*` rows.
- **Approve/merge layer (the seam the future SUBMIT/Plan 1 reads; NOT the replay).** Per-flagged-row **Approve** toggle (un-flagged fields are approved-by-default — lower friction); a header strip with progress + "Approve all reviewed" + a **disabled-until-`submit_ready`** "Approve & continue to submit" button that does **NOT** submit. `approvalEnvelope(entries)` (pure) → `{to_approve_count, approved_count, pending_count, unreplaced_placeholders, all_approved, submit_ready}`; **`submit_ready` = every flagged field approved AND no unreplaced AI placeholder**. A VALUE edit RESETS that field's approval (re-review); a soft-deleted entry is excluded from the denominator; `effectiveValue(entry)` → `{value, kind, approved, deleted}` is the documented value SUBMIT will replay.
- **Review-page CHECK (the end-to-end fill-verify; `RUN_CDP_REVIEW_CHECK` / `cdp-review-check`).** The final Workday review page renders every value ACTUALLY in the form as read-only text — ground truth. `cdpReadReviewPage` (self-contained) scrapes those displayed values and the PURE `reconcileReviewPage` (lib.js, `test/review-reconcile.test.js`) diffs them vs the saved `reviewSummary`; a divergence flags a fill bug (the value-revert class). READ-ONLY: attach → read → detach, **never clicks Next/Submit**. **VALUE-PRESENCE, not label-match** — the observed review DOM has NO reliable field labels (bare `<span>`/`<div>`), so a DISTINCTIVE recorded value (≥4 chars, or ≥3 and not a generic yes/no token) AGREES iff it appears in the page text (digit relief for phones "8506660266"↔"+1 850-666-0266"; region name↔abbrev relief "Florida"↔"FL"), while SHORT values ("Yes"/"No") + CHECKBOXES fall back to LABEL-ANCHORING on the distinctive question text (`normL` strips the trailing required "*"/"**") and FILE_UPLOAD matches the résumé filename. The scraper feeds VALUE HINTS from the bundle (value-anchoring: locate each recorded value → tag with its true label). Buckets: AGREE / DISAGREE (page value ≠ recorded) / MISSING (recorded but nowhere on the page — didn't-stick) / EXTRA (a distinctive page value the bundle doesn't hold) / AMBIGUOUS. Output `[REVIEW-CHECK]` in the SW console.

## Onboarding walk (pre-form: JD → apply → login → verify; SW-driven, NEVER submits)

The stage BEFORE the fill walk: drive the active tab from a job-description page to a filled-in
application form. Port of the Playwright repo's `workday.py` (navigate_to_first_form_page →
handle_application_modal → handle_auth_screen → _handle_email_verification), on the CDP substrate,
hardened. **Live-verified visible + hidden** across Comcast, altasciences (wd1 — create → Gmail
verify → activate → re-sign-in → form), and Palo Alto Networks (wd5 — social-login chooser).
Orchestrator `runCdpOnboard(tabId, {credentials, gmailEnabled, startUrl})` (background.js);
handler `RUN_CDP_ONBOARD`; setup + caveats in `docs/gmail-setup.md`. **One-time setup required** (pinned
extension key + a Chrome-Extension OAuth client) — see that doc.

- **Reuses the CDP primitives, adds navigation.** New in cdp.js: `cdpNavigate` (`Page.navigate` — for the verify link + an optional start URL) + `cdpReload` (`Page.reload` — the soft-error refresh). Reads via `cdpOnboardScan` (self-contained; url/host/bodyText + apply/auth/form markers + `hasAuthEl`). Clicks via the walk's cover-check/auto-dismiss ladder (`cdpCoverCheck` + `cdpFindDismissControl` + `cdpClickAt`; `cdpCoverCheck` treats a Workday `click_filter` overlay as the click surface, not a blocker). Types via `focus → cdpSelectAllDelete → cdpInsertText → read-back`. NO input-lock (a takeover halt must leave the operator free to act). Detaches in `finally`.
- **Runs hidden-safe (adaptive pacing).** ALL click/type/transition pacing goes through the local `pace()` = `cdpAdaptiveDelay` (the fill's `act.delay` model): ~10× faster when the tab is VISIBLE/worker-timers-fast, FULL (throttle-immune) when hidden — every `pace()` site is gated by a read-back/poll/scan so a too-short fast wait only costs a retry. Transition waits (`settlePage`/`waitFor`) additionally `cdpWakePage()` each tick; `cdpInstallPageOverrides` (worker-timers) is installed at start. The ONE exception is the **5s post-activation settle** — a real server-commit wait (`cdpDelay(5000)`, never scaled): signing in the instant after the activate link leaves the account "pending verification" and re-triggers a 2nd email (the PANW double-cycle). First-run Gmail consent needs the interactive account picker; once the token's cached, subsequent runs are silent → hidden-friendly.
- **The decisions are PURE + unit-pinned (lib.js):** `pickApplyTarget` (chain `adventureButton → continueButton → applyManually`, first present wins; NEVER `useMyLastApplication`); `classifyAuthOutcome` (bodyText + form state → `verify`/`wrong_credentials`/`success`/`unknown`; success = a real form field present AND `!hasAuthEl`); `isWorkdaySoftError` (the "Something went wrong / please refresh" page — apology AND a refresh cue); `looksLikeSso` (idp/saml/okta-style URL, or a sign-in button with no email/password field). `test/onboarding.test.js`.
- **Sign-in FIRST, create-account on wrong-creds.** The auth loop (`doAuth`, capped attempts): try sign-in as the stored credentials → classify → `success` land on form; `verify` → Gmail flow → re-sign-in; `wrong_credentials` → `doCreateAccount` (email/password/`verifyPassword`-or-2nd-password/consent-checkbox/`createAccountSubmitButton`; "already exists" → fall back to sign-in) → loop. Credentials are FIXED (`data/credentials.json` → storage — NON-dot, because Chrome won't serve a dotfile from an unpacked extension via `getURL`; same email reused per tenant — that's why sign-in-first works). The same Gmail `+alias` account works across all tenants.
- **Submit resilience + tenant variants.** Both submits (Sign In / Create Account) go through **`submitAndWait`**: click → wait for the outcome → **re-click if the form is still up** (up to 3 attempts) — the fallback for a raced/not-yet-enabled button (a scaled-fast click can land before Workday enables it). A pre-submit `cdpDelay(500)` (FIXED, not paced) lets the button enable first. Workday's own transparent **`click_filter`** overlay is treated as the click surface (`cdpCoverCheck`), not a blocker. A **social-login CHOOSER** (`SignInWithEmailButton` + federated Apple/Google/LinkedIn we NEVER click; PANW) is revealed by clicking "Sign in with email"; if that reveal can't repaint hidden it halts `hidden-render-stalled` (foreground + re-run). An **existing-but-unverified account** (sign-in → `verify` showing a "Resend Account Verification" button, `cdpResendVerifyRect`) gets Resend CLICKED before polling Gmail — the original email is stale/expired. This makes the flow idempotent across re-runs of the same `+alias`.
- **Gmail auto-verify (`gmail.js`, adapter mirroring llm.js — never-throws, UMD, injectable fetch/now/sleep, `gmail.readonly` ONLY, all data CLIENT-SIDE).** `chrome.identity.getAuthToken` (Chrome owns the account picker + token cache/refresh — no stored token). `gmailFindVerificationEmail` polls `newer_than:1h (myworkdayjobs OR from:workday.com)` (5s/120s) — **sender-agnostic** because some tenants send from `Workday@<tenant>.com`, not workday.com (PANW), so it keys on the `myworkdayjobs` link-token in the body; freshness-guards by `internalDate`, walks the MIME body (base64url), and extracts the first `http(s)` URL containing the TENANT HOST (preferring an `/activate`-style link over a job-listing link on the same host) → `cdpNavigate` to it → **5s activation settle** → re-sign-in. A 401 refreshes the token once. `test/gmail.test.js`. **Gmail smoke test** (`RUN_GMAIL_TEST` → `runGmailSmokeTest`): getToken + a readonly `users/me/profile` call — run FIRST, shows the connected inbox.
- **Refresh feature (operator-requested).** Workday's transient "Something went wrong / Please refresh…" → `maybeRefresh` reloads ONCE (capped at 2/run) and retries; persists → surfaces, no reload loop.
- **Safety / halts.** NEVER submits; never clicks an affirmative consent-popup control; refuses SSO (`sso` halt → manual login then re-run). Every human-needed stop returns `needs_operator` + a self-explaining `stopped`/`detail` (SSO / no-credentials / verification-required-gmail-off / verification-email-not-found / verify-link-invalid / apply-*-blocked / auth-unknown). **Contract:** `ok:false` ⇒ a CRASH only (attach/navigate/exception); a needs-operator outcome is `ok:true` + `needs_operator`. **Verify links MAY be session-bound** (operator flag) — the flow navigates the tab to the fetched link and halts `verify-link-invalid` if the tenant rejects it; confirm end-to-end per tenant before trusting auto-verify.
- **Hand-off.** By default onboarding STOPS on the form (`reached_form`) — it does NOT auto-run the fill walk (which ADVANCES a live application). The `RUN_CDP_ONBOARD` handler chains into `runCdpWalk` ONLY when `onboardConfig.continueToWalk === true` (popup toggle, OFF by default; keep off until on a DISPOSABLE application). Popup: **Onboarding** section (Load credentials / Start URL / Gmail toggle + Connect-test / continue-to-walk toggle / Start).

## Multi-page walk (SW-driven; NEVER submits)

Workday applications span several pages (My Information → Experience → Questions → … → Review). Live on both substrates: the page-engine `runWalk` and the CDP `runCdpWalk` (the N-page loop; `WALK_MAX_PAGES=8` backstop). Standing rules:

- **The engine is torn down on every page transition** → the loop CANNOT live in the engine; it lives in the **service worker**, driving the ACTIVE tab per page (never a background tab). Per-page flow: fill → persist that page's review bundle → **the SW clicks Next** (`clickNext`/`clickPageNext` — a separate guarded step AFTER the fill result is captured + persisted, so triggering navigation can never drop review data) → wait for the new page → repeat. **`clickPageNext` handles a COVERED button**: it `elementFromPoint`-checks the button's center before the coordinate click — if a popup/overlay (e.g. Simplify's dialog, a cookie/consent modal) sits on top, a click would be swallowed and look like a bare nav-timeout. It first attempts a **best-effort auto-dismiss** (`cdpFindDismissControl`): click ONE clearly-dismissive control (X / Close / No-thanks — **never** Accept/Agree/OK/Got-it, consent-safe) inside the popup — **shadow-DOM aware** (Simplify renders into `div.simplify-jobs-shadow-root`, so the X lives in `host.shadowRoot`, invisible to a light-DOM query; a CLOSED shadow root → not-found → safe halt), never force-removing DOM — then re-checks and proceeds if clear (`{clicked:true, dismissed}`). If no safe control is found or it stays covered, it halts `click-refused:blocked` + logs the blocker (`blockedBy`) for the operator.
- **Transition wait is poll-based, never a fixed delay.** Page engine: `waitForNextPage` re-injects a tiny `probePage` every ~400ms (15s ceiling); injection errors mid-navigation = "not ready, keep polling", not a failure. CDP: `cdpWaitNextPage` — the debugger attach SURVIVES navigation (no re-injection), with a ~1s fast-exit when validation errors render without an advance. **Page signature = `url || pageId || formFieldIds` (any one differing = advanced) — `pageId` alone is NOT sufficient:** the `applyFlowPage` container id is shared across pages; the `formField-*` set delta is the load-bearing signal.
- **Termination: stop at the review page, NEVER submit — double guard.** The footer Next button **reuses the same automation-id as Submit** on the review page (marker `data-automation-id="applyFlowReviewPage"`). Guard 1: the walk stops when the marker is present — checked at the TOP of each iteration, before any fill or click. Guard 2: `clickNext`/`clickPageNext` independently refuse (`{refused:"review-page"}`) — defense in depth on the one click that could submit an application. **HARD GATE: the first walk that actually reaches the review page must be watched eyes-on on a DISPOSABLE application.**
- **Required fields block advancement → graceful halt, never a guess.** Workday won't advance with a required field empty: the signature never changes and the walk halts `nav-timeout` with diagnostics (page error samples + the fields left empty because the profile has no value). A dirty-state nav-timeout means "eyeball the page", not "session expired".
- **Session death is behavioral, not DOM-static** (a timed-out page is DOM-identical to a live one — recon-refuted static detection). `sessionLooksDead(state)` (lib.js, pure) = `vpsErrorPresent` OR session banner OR login marker OR no-form — NEVER keyed off validation-error markers (a form showing validation errors is alive). The walk halts "session expired" on dead, and `resume-not-attached` BEFORE clicking Next if the resume didn't attach. Narrow early-warning: `sessionWarning` when the `source` field's options never loaded.
- **Accumulation (decision RESOLVED): write-per-page.** Each page merges into ONE `reviewSummary` via `accumulateBundle`/`persistAccumulated` (merge key = the field-set `page`); the walk clears `reviewSummary`+`reviewAudit` ONCE at start, OUTSIDE the loop (a mid-walk clear would wipe accumulated pages).
- **AI-4 remediation (the nav-timeout branch, `remediatePageErrors`):** **never acts blind** — polls for the error banner (it renders LATER than the fast-exit) and hard-gates every attempt on non-empty EXPANDED error text (`expandErrorSamples` splits Workday's single concatenated banner element on the `Error-` prefix + drops `[role=alert]` success toasts; clean halts `no-error-text` / `errors-cleared-not-advancing`). Ladder: **Tier 0** dup-language delete-all (real-vs-phantom from audited results) → **Tier 1** deterministic re-fill of the mapped fields the error text names (`onlyFieldNames` — no AI) → **Tier 1.5** deterministic DELETE of error-named repeating rows that read EMPTY on the live page (a value-holding row is never deleted; a nested name deletes ONLY nested rows, the parent untouched; an unreadable probe leaves the row alone) → **Tier 1.6** section re-fill (`onlySections`; `preserveExtras` — remediation NEVER reconciles down, manually-added entries survive) → **Tier 2** AI last-resort (whitelisted refill/delete_entry/none, sanitized by `parseRemediation`). Global cap + halt-on-no-progress (`errorSetUnchanged`); every action recorded `ai-remediation`; the submit double-guard untouched.

## Resume upload & storage

The resume is NOT picked from the OS filesystem per application. *Why:* the end state generates a per-application AI-tailored resume variant (or one fixed resume), so the bytes are held/produced inside the extension and attached programmatically — a picker is incompatible with generated variants and hostile to the high-volume queue-and-run premise.

- **Storage (`db.js`):** one PDF uploaded in the popup → **base64 in IndexedDB** (DB `ApplyPilot`, store `resume`, single fixed key **`resume:default`** → `{filename, mime, size, base64, savedAt}`). IndexedDB, not `chrome.storage` — a real resume's base64 blows past its quotas and binary document bytes don't belong there. `db.js` loads in three contexts off ONE file (popup `<script>`, SW `importScripts`, Node `require` — UMD-lite), which makes it unit-testable (fake-indexeddb). **Phase 2+ (AI-tailored per-application variants) just adds more keys to this same store — do NOT pre-build variant slots or per-application keying.**
- **Attach (`attachResume`, self-contained):** **strings only across the injection/message boundary — a `File`/`Blob` serializes to `{}`.** The SW reads the base64 from IndexedDB and passes it as plain STRING args; the injected fn rebuilds the `File` in the page, sets `input.files` via a `DataTransfer`, and dispatches `change` (Workday's delegated React `onChange` fires). It first **clears existing attachments** one-at-a-time, **re-resolving the section/items/`delete-file` fresh from `document` each pass** — Workday swaps the subtree mid-loop, so a captured ref goes stale and caps deletion at n−1.
- **Success = the confirmation ROW, not the input:** `input.files` RESETS to 0 after Workday's XHR upload. Gate specifically on **`file-upload-successful`** (`file-upload-item` renders first, before the success marker).
- **Wiring:** page path = the SW post-fill step `attachResumeForPage` (both `RUN_FILL` and the walk). CDP path = `cdpEval(attachResume, …)` on the SAME debugger attach, inside `fillAndPersistPage` (after `drivePageFill`, before the bundle build), patching the `file_upload` record to `filled`; no-resume / failed attach → `needs_review` and the walk halts `resume-not-attached` BEFORE clicking Next (self-explaining, not a bare nav-timeout). The attach bumps `window.__apActing` so the input-lock doesn't swallow its synthetic delete-clicks. Per-entry attachments (e.g. per-cert) are the operator's job (form / review picker) — the résumé only ever attaches to the top-level Documents field (regression-pinned). New-tenant probe: `RUN_CDP_RESUME_RECON`.

## Repeating sections — WE / Education / Websites / Languages / Certifications

Page 2 (My Experience) is repeating multi-field sections, all driven by one machinery on both substrates: page engine `fillRepeatingSection` + `fillMappedEntry`; CDP `driveRepeatingSectionCdp` + `fillEntryCdp`. Full DOM detail: dom-patterns 2026-06-04 / -16 / -17 / -18.

- **Reconcile to exactly N, then fill each entry** (true idempotency, proven from ARBITRARY dirty state): Add→mount up to N (count-polled, bounded), delete trailing extras via `deleteEntryButton`. Per-entry fill is config-driven over a `fieldMap` of `{field|labelRegex, name, widget, key, path}` — **`labelRegex` for hashed `formField-*` ids** (Languages proficiencies; entry-scope holds even with IDENTICAL hashed ids across entries). Values run through `resolve()` (tiered-array passthrough). Entry fields fill in the entry's scanned DOM order; sections drive in page order (`sectionsInDomOrder`); entries re-resolved fresh each iteration (re-renders).
- **Maps:** `WORK_EXPERIENCE_MAP` — currentlyWorkHere checkbox FIRST (it controls the To box) → text → M/Y dates → roleDescription `<textarea>` ← `bulletsText` (Profile v2: `prepareProfile` derives `bulletsText` from the profile's single `role_description` textarea; legacy `bullets[]` is the `joinBullets` fallback); `currently_work_here:true` skips endDate, but `todayIfStuckRequired` fills TODAY + `we-currentwork-today` flag if the To box stays present AND required. `EDUCATION_MAP` — school / degree / fieldOfStudy / gpa + **year-only** dates. `WEBSITE_MAP` — `url` via `ensureHttps`. `LANGUAGE_MAP` — language dropdown + BY-LABEL proficiency dropdowns + the `_allFluent` "I am fluent" checkbox LAST (Profile v2: `prepareProfile` uses the human-set `languages[].fluent` when present, else derives from reading∧speaking∧writing). **`prepareProfile` reorders the languages list so any English entry is filled LAST** — the operator found English-last reduces Workday's spurious "duplicate languages not allowed" ghost error on Save & Continue (stable partition; non-English keep their order). `CERTIFICATION_MAP` — certification typeahead + number + full **M/D/Y** dates + the **NESTED Specialties** sub-section (`CERT_NESTED`/`fillNestedSpecialtiesCdp`: a repeating section nested inside a repeating entry; per-cert-entry-scoped Add/Delete; reconciles orphan empty rows away even at N=0; wrapper selectors probed live per field by `cdpNestedFieldSel` — the fkit↔formField relationship is tenant-variable, nothing hardcoded; records nested-canonical `certification[i].specialties[j].*`, grouped under the parent in review).
- **`deleteOnNoMatch` (Languages, Certifications only):** an optional pick-section entry whose REQUIRED pick ends a **GENUINE** no-match (options rendered but absent / every candidate definitively negative) is DELETED so it can't block Next; a transient/infra failure KEEPS + flags (unit-pinned — a render hiccup must never destroy valid entries); a `filled_review` commit (containment/fuzzy) KEEPS the entry. WE/Education/Websites: flag, never delete. Nested child rows: a required pick ending BLANK on a definitive negative is deleted at fill time (value-holders + transients never). An entry of all-AI-rescuable typeaheads isn't deleted when AI is on.
- **Key DOM facts:** entry containers are `[data-fkit-id^="<section>-"][data-fkit-id$="--null"]` — the From/To date wrappers share the prefix, so a bare prefix over-matches (one entry → 3 nodes). **`formField-*` ids DUPLICATE across entries** → every field access MUST scope to the entry container (the flat driver loop skips fields inside repeating containers — `isRepeating`). **Add buttons all share `data-automation-id="add-button"`** ("Add" / "Add Another") → anchor by section heading (nearest-heading regex, `findSectionAdd`; nested Adds carry `insideEntry` — any `-<digits>--` fkit ancestor — and are excluded from page-level logic). Dates are `role="spinbutton"` composites (M/Y, year-only, M/D/Y) parsed **SW-side** by the pure `parseYearMonth`/`parseYear`/`parseYearMonthDay` (lib.js — the injected engine can't import; rejects placeholders/out-of-range). Profile lists are SW-prepared (`prepareProfile`, `meaningfulEntries`); profile-side tiered candidate lists (degree, field_of_study) live in the profile, not the filler.

## CDP off-loop actuation — the primary fill path

A hidden/minimized tab throttles page timers to ~1Hz then deep-freezes, so a page-injected fill stalls (a PASSIVE debugger attach does NOT relieve it). Fix: actuation as **CDP commands from the service worker** (`chrome.debugger`, the `"debugger"` permission) — `Input.*`/`Runtime.evaluate` execute off the page loop, throttle-immune. Workday's debounced REACTION still runs page-side and throttled → **all waits are generous SW-side wall-clock; Δperf ~1000ms during a run is EXPECTED, never failure.** Full empirical detail: dom-patterns 2026-06-12 onward.

- **Substrate/brain split (the substrate-swap hedge):** `cdp.js` = the substrate — attach/detach lifecycle (detach in `finally`; external-detach/tab-close listeners; **ONE debugger client per tab**, so page DevTools on the tab kills the attach), trusted input primitives, `cdpEval` DOM reads, `makeCdpActuation()`. `fill-driver.js` = the brain (`drivePageFill`): `FIELD_MAP`/`resolve`/employer-match/record+status semantics calling ONLY the actuation interface — Node-testable with a fake actuation (`test/fill-driver.test.js`, incl. the NAMED invariant test that the previous-worker radio is never left "Yes" without a review flag). ALL pacing goes through `act.delay` (SW wall-clock) — **never a page-side timer**; every element is re-resolved fresh per call (React re-renders orphan held nodes — recon-proven).
- **Pacing + verify model:** `act.delay`/`act.delayRender` are **adaptive** — ~10× faster (`FAST_FACTOR 0.1`, floor 10ms) when `cdpFast()` says fast, full otherwise; **`act.delayFull`** stays never-scaled for the few waits that must always run full (the M40 audit settle). **`cdpFast()` = tab VISIBLE, OR hidden-but-worker-timers-measured-fast** — never fast on assumption. **Hidden-tab SPEED (worker-timers, 2026-07-04):** the injected `buildOverrideSrc` routes the page's `setTimeout`/`setInterval` (+ rAF) through a `blob:` Web Worker whose timers ESCAPE Chrome's background throttle, so a hidden fill runs at page-speed instead of ~1Hz; fast pacing is gated on a MEASURED in-page `setTimeout(0)` round-trip (`cdpTimersFast`, a non-blocking `Promise.race` bounded to ~200ms), so a CSP-blocked worker / genuinely-slow page ⇒ **byte-identical slow path** (no false-verify). **`act.delayRender`** (adaptive, same `cdpFast()` gate) carries the render-SETTLE intervals (dropdown option-settle + commit-persistence; recon opens/closes) — safe because each is gated by an interval-length-INDEPENDENT state check, not the wait length. `forceWorkerTimersOff` (chrome.storage.local) forces the slow path for regression testing. Nothing proceeds on a fixed timer — every wait polls the page condition it gates: open-retry on an aria-expanded gate (**toggle-shut invariant — never re-click an expanded trigger**, a 2nd click closes it); text/date read-backs poll until the COMPLETE value registers (ceiling = give-up only); the dropdown option-settle waits for COMPLETE render before picking and the commit-verify adds a **PERSISTENCE re-read** (a momentary pick discarded on render-complete is never reported filled — the false-verify class, the ONE failure the safety contract exists to prevent). **M40 post-fill audit:** a SECOND, independent DOM read after the whole page settles, reconciled vs what each field recorded (re-read by widget type via the retained `auditLoc`, re-resolved fresh) — match / mismatch (`needs_review`/`audit-mismatch`, `after` = the live truth) / unverifiable (`audit-unverifiable`, never a silent pass); inline (auto, may self-heal with ONE re-fill then re-read) + standalone flag-only re-audit (`RUN_CDP_AUDIT`). The initial re-read is **BATCHED into ONE `Runtime.evaluate`** (`act.readAuditRaw` → `cdpReadAuditRaw`, which COMPOSES the single-source reader fns — no body dup) instead of one `cdpEval` per field — cuts N serial round-trips to 1 (biggest win on HIDDEN, where each round-trip costs most); the `{actual,readable}` mapping stays SW-side (`auditActualFromRaw`, Node-tested), and a missing/failed batch falls back to the per-field path (the mismatch→refill re-read stays per-field). Text/date fills also self-heal (one retry on read-back mismatch). `already-filled*` records are audit-EXCLUDED (never re-actuated).
- **Simple widgets:** text = `Input.insertText` (trusted `beforeinput`+`input`, survives blur) after CDP click-to-focus + trusted Ctrl+A/Delete clear, read-back-verified; `<textarea>` = same path with a `tag` param (insertText handles the newline). Dates = per segment, **triple-click the visible `dateSection*-display`** (the `-input` is 0-box — coordinate-click impossible) → focus-verify (never type into an unfocused segment) → type digits → parseInt read-back; **⛔ NO Ctrl+A in the date path** — it selects the WHOLE composite + resets focus to Month, piling digits into Month (a `node --test` guard pins that the composite never whole-field-clears; triple-click-select + type-replace needs no clear). Radio/checkbox = coordinate click on the `<label for>` (fallback: focused input + Space), verified via `checked`. M29 retry: rect/focus reads re-poll to a ceiling (absorbs throttle transients; `gave up` logs suggest session-death, not throttle). **Dropdowns:** commit = **TEXT-KEYED scroll+click** of the matched option scoped to the trigger's aria-controls listbox (a coordinate click on an out-of-view option lands outside the popup and dismisses it — the "Uruguay pitfall"; no type-jump/arrow-counting — native type-ahead cycles same-prefix values), exact-normalize verify + persistence re-read, one retry then `needs_review` (never a wrong/silent commit); **OVERWRITE commit — ESCALATING BEAT LADDER** — committing a RE-SELECTION (replacing a real prior value, e.g. pre-filled+flipped languages) fails under too-fast pacing (the click lands on the right option, `hitTarget=true`, but doesn't fire the selection — a Workday-internal option-click DEBOUNCE with NO DOM correlate; elapsed-time-since-open is the only lever). The debounce is a PAINT thing — tiny when the tab is painting, ~700ms when not. `act.visible` (`cdpVisible` = tab active + window not minimized; NOT `cdpFast`) picks the STARTING beats, **BUT it can't detect OCCLUSION: a tab alt-tabbed BEHIND another app is throttled/not-painting yet still reports `tab.active && !minimized`, so `act.visible` mislabels it "visible"** — and the page's own `visibilityState`/`rAF` are spoofed/polyfilled by the hidden-tab overrides, so paint can't be read there either. So the commit no longer TRUSTS the label: `overwriteBeatLadder` returns an ASCENDING ladder (**VISIBLE `[30,100,700,5000]`, HIDDEN `[120,700,5000]`** — each ends with a FINAL ~5s safety tier `overwriteMaxBeatMs` for a deeply-throttled/occluded tab that even 700ms misses) and the commit **ESCALATES on each MISS** — re-open + wait the next-larger beat since (re-)open — up to the 5s tier REGARDLESS of the label. A painting tab commits on tier 0 (no penalty); a mislabeled/occluded/hidden tab self-corrects to the big beat instead of failing to `needs_review` (the alt-tab language-swap bug, fixed 2026-07-07 — the old visible pair capped at `100` and never reached `700`). Non-final tiers fail-fast (`min(overwriteFailFastMs, commitCeilingMs)`) so a MISS escalates cheaply; the last tier gets the full ceiling. EMPTY fills (`before` = placeholder) never race → single fast commit, no ladder. A `[CDP-DD-REFILL]` line per overwrite (prints the ladder + which tier committed) lets the operator retune. The commit-PERSISTENCE re-read still gates every accept → escalation can only cost extra re-opens, never a wrong fill (unit-pinned, incl. that a mislabeled-visible tab still reaches the `700` tier). EMPTY fills (`before` = the disabled placeholder) never race → single fast commit, no beat; **tier-aware pre-filled guard** — the FILL keeps zero-actuation if the pre-fill is tier-0 (`dropdown-prefilled-kept`); the end-of-page `captureChoiceOptions` then re-opens it READ-ONLY to scrape options for the review editor so a page-1 dropdown (country/state/phone) renders as a real `<select>`, not a textbox (value preserved, M40-audited — 2026-07-05 operator ask; the old literal "never re-open a tier-0 pre-fill" is relaxed to "never value-change one"); `k>0` re-opens + upgrades to the highest offered tier (`dropdown-overwrite-success` / `-better-tier-unavailable`); `k===-1` full walk.
- **Hierarchical typeahead — ONE filler for typeahead + source + cert trees** (`fillTypeaheadCdp`; cert and "How did you hear about us?" are the SAME Workday multiselect; `fillSourceCdp` is a kept alias): ONE reader `cdpReadHierState` (leaves = `promptOption`/`data-automation-label` — NOT role=option; `promptLeafNode` selected-state; scoped by `data-uxi-multiselect-id`; chips/`selectedItemList` excluded — a committed chip elsewhere embeds a promptOption). ## Working principles

- **Trace the real DOM before writing a handler — don't guess.** Every hard bug (the `source` picker, the dropdown chip contamination) only cracked after blind guesses failed and we instrumented a read-only trace of the *actual* DOM, then built from what it showed. Guessing widget shapes wasted rounds; tracing settled them — make a discovery trace the first step on any new widget/tenant.
- **Incremental:** one focused change per milestone, verified on a real page. No skipping ahead.
- **Observation-driven:** rules in `docs/dom-patterns.md` come from observed DOM, not assumptions; keep code and doc in sync.
- **Don't port the Python repo blindly:** it's a design reference (intent, prompts, edge cases), not code to mechanically translate to JS.
- **Commit per milestone:** each working milestone gets a commit, so we can bisect when something breaks.
- **Keep this file lean:** standing rules and invariants only. When a milestone lands, update the relevant rule section here (a few lines) and append the full dated entry to `docs/progress-log.md`; observed-DOM findings go to `docs/dom-patterns.md`.
- **Three consoles:** service worker (`background.js` + the engine's returned data), page F12 (anything `console.log`'d inside the injected function), popup right-click → Inspect (`popup.js`). Most `[ApplyPilot]` output is in the service-worker console.
