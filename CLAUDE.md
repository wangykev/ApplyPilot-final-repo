# ApplyPilot Chrome Extension

Docs: `docs/dom-patterns.md` (the observed-DOM rulebook) · `docs/progress-log.md` (full milestone history — append new milestone entries there).

## What this is

A Manifest V3 Chrome extension that automates Workday job applications from a stored profile. From-scratch rewrite of a Python + Playwright tool of the same name; the Python repo lives separately and is a **design reference, not code to port** — it documents what the system should do; this repo builds it for the runtime that will ship. The shape is a **fill → review → submit** pipeline: the engine fills a page and produces a per-field review summary, a human reviews/edits it, and a later pass replays the approved values. All three stages are built; the SUBMIT stage is live-verified in **SIMULATE mode** (it runs the full replay + precondition gate and logs "would click submit" — no real click yet; going live is one flag flip behind an eyes-on, disposable-app gate).

## Architecture & invariants

- Manifest V3; host permissions `*://*.myworkdayjobs.com/*` **and `*://*.myworkdaysite.com/*`** (the logged-in Workday host — needed so the website-Run JD scrape's `chrome.scripting.executeScript` can read the page; the CDP walk works there regardless since `chrome.debugger` isn't host-gated), plus `www.linkedin.com` / `app.joinhandshake.com` / `raw.githubusercontent.com` for the discovery sweep. **Deliberately NOT `<all_urls>`:** discovery reads arbitrary employer/ATS job pages through CDP instead (see Job discovery).
- **Active-tab injection — NOT a content script, NOT a background tab.** `background.js` (service worker) receives a `RUN_FILL` message from the popup and uses `chrome.scripting.executeScript` to inject `fillEngine` into the active tab (frame 0). *Why:* the operator is logged in and on the form themselves, so injecting into the active tab fills the page they're looking at. Content-script files and background-tab/multi-page automation were deliberately deferred — not needed for active-tab fill.
- **Profile + defaults + jobContext live in `chrome.storage.local`** — the permanent website→extension handoff contract. The engine ALWAYS reads them from storage (today the popup's "Load default profile" seeds `profile` from `data/profile.json` and `defaults` from `data/application_defaults.json`; `jobContext.company` is set via a popup field; later a website will write them). The engine is agnostic to how they got there.
- **"Engine computes / service worker does I/O."** The injected `fillEngine` is self-contained (closes over nothing from the SW), reads/writes the page DOM, and RETURNS results — it never touches `chrome.storage`. `background.js` does all storage I/O (e.g. persisting the review summary). Keep this boundary.
- **Pipeline shape:** fill (engine, per page) → review (the `reviewSummary` + `summary.html` viewer/editor, human edits) → submit (replay approved values; not built).
- **UI:** `popup.html`/`popup.js` — profile/resume/LLM config + the fill, recon, and walk buttons (see CDP section → Entry points). `summary.html`/`summary.js` — the review-summary viewer/editor. `[ApplyPilot]` logs land in the **service-worker** console (see Working principles → three consoles).

## Workday DOM model

See `docs/dom-patterns.md` for the full, dated rulebook (every observed tenant + refutations). Short version:
- Every form field sits in a `<div data-automation-id="formField-*">` wrapper.
- `classifyField` derives the widget type from wrapper descendants, first match wins: **hierarchical `source` → typeahead (`data-uxi-widget-type="multiselect"`) → radio (`input[type=radio]`) → dropdown (`button[aria-haspopup="listbox"]`) → checkbox (ONE) → checkbox_group (2+ checkboxes in one wrapper = a pick-one set, e.g. the OFCCP disability self-ID; radio-like fill — label-EXACT, unchecks the current option first, verifies exactly one ends checked; options read from the DOM by the scan, so a field left BLANK still reaches review as a picker) → **date** (a `dateSection*-input` composite — its spinbuttons carry no `type`, so 3 of them used to read as "not one text input" → `unknown` → a bare textbox in review; the scan carries `dateSegments` → `date_order`, so review renders the form's own MM/DD/YYYY vs MM/YYYY vs YYYY) → text → unknown**.
- **Rules come from observed DOM, not the Python spec.** Patterns the spec assumed do NOT hold on observed pages (e.g. `role="combobox"`, `role="radiogroup"` don't fire on Comcast). When code and doc disagree, fix one — don't let them drift.

## React fill technique

Workday is React-based: `input.value = "x"` updates the DOM but not React's internal state, so the value reverts on submit. The working pattern (verified on Comcast text fields; needed for any controlled input):
1. native setter: `Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype, 'value').set`
2. `nativeSetter.call(input, value)`
3. dispatch `new Event('input', { bubbles: true })`
4. dispatch `new Event('change', { bubbles: true })`

## Interaction patterns (the shared helpers)

Primitives proven against real Workday pages, now the shared helpers inside `fillEngine` (`background.js`). Reuse them — don't reinvent.

- **`robustClick` — the click primitive.** Three-strategy ladder: (1) pointer-event sequence (`pointerdown→mousedown→pointerup→mouseup→click`, `clientX/Y` from the bounding rect — closest analog to a real click), (2) native `el.click()`, (3) bare `MouseEvent('click')`. On Comcast the pointer sequence has succeeded on every widget; the fallbacks are kept because portaled-listbox/overlay layers can mask synthetic clicks on other tenants. Use it for any non-text-input interaction.
- **Typeahead is open-before-find.** The searchBox `<input>` isn't reachable until the widget opens (container carries `data-automation-hiddensearch="true"`). Click the opener first, then `waitFor` `input[data-automation-id="searchBox"]` scoped to the wrapper. Opener ladder: `[data-automation-id="multiselectInputContainer"]` → `[data-uxi-widget-type="selectinput"]` → first `<input>` → wrapper.
- **Clear before typing.** Set the search input to `""` (native setter + input event), wait briefly, then type — avoids residual-text contamination on re-fill.
- **Settle-poll the filter, don't scrape on a fixed delay.** Live-filtering typeaheads race a fixed `setTimeout` (we saw option counts flip 21↔1 with wrong matches). Poll the enabled-option count ~120ms and accept only after **two consecutive equal, non-zero reads**, with a timeout fallback to the latest read.
- **Sequential cleanup — don't over-engineer per-field close.** Moving to the next field blurs the prior widget and dismisses its listbox for free. We burned time on explicit Escape/click-outside closes before realizing the sequence handles teardown. Per-field handlers focus on open+select; only the last field could leave a listbox open (cosmetic).
- **Radios: click the label, group by `name`.** Inputs are CSS-clipped; the `<label for="<id>">` is the styled click target (native label-activation flips `checked` + fires the change event React listens for). Group by shared `name` (not a `role="radiogroup"` wrapper, which Comcast omits). Verify via `input.checked`.
- **Options are portaled to the document root** (outside the `formField-*` subtree). **But a bare page-wide `[role="option"]` scrape is contaminated** — scope dropdown scrapes to the field's own listbox (see DOM lessons → chip contamination + aria-controls scoping). Filter `aria-disabled="true"` (the "Select One" placeholder).
- **Always verify state, not just click outcome.** `robustClick` returning a strategy means an event fired, not that the page updated. Re-read observable state after a delay: radios → `input.checked`; dropdowns → trigger text; typeaheads/source → the `selectedItem` chip / `multiselectlistitem` selected-state. Synthetic clicks have no-op'd silently.

## Choice-widget handlers & hard-won DOM lessons

These cost multiple rounds; full per-tenant detail is in `docs/dom-patterns.md`. The load-bearing whys:

- **`source` ("How did you hear about us?") has three tenant shapes**, all handled by `fillSource` (discover-and-trace): Cambium = button+listbox **expand-walk** (no searchBox); Comcast = typeahead; **US Bank = searchBox that filters on ENTER, not live**, whose result leaves are `<div data-automation-id="promptOption" data-automation-label="…">` — **NOT `role="option"`** (that role is on a sibling `menuItem`), and whose searchBox `aria-controls` points at a `promptAriaInstruction` node (the wrong target). So: type → full Enter → race-safe wait for `promptOption`s → match on `data-automation-label` → click → **commit-gated** via the enclosing `multiselectlistitem` selected-state (so no false "filled").
- **Dropdown option contamination — and why visibility filtering is a DEAD END.** A page-wide `[role="option"]` scrape pulled in two *genuinely-visible* contaminants: (1) **selected-item CHIPS** — a filled multiselect/source renders its selected value as `<ul role="listbox" data-automation-id="selectedItemList"><li role="option" data-automation-id="selectedItem">…</li></ul>`, i.e. **the chips carry `role="option"` markup**, so "LinkedIn"/"(+1)" showed up as options inside every dropdown; and (2) **a prior dropdown's listbox stays open** (filling State, Country's `ctny0` was still mounted, so State listed countries). **Visibility filtering was tried TWICE and confirmed a dead end — do not retry it**: both contaminants are genuinely `visible:true` (the chips are shown; the prior listbox is still open), so a visibility filter can never remove them. **Fix:** scope the scrape to the trigger's own `aria-controls` listbox (verified per widget: `ctny0`→countries, `ctny1`→states, `ctny2`→phone-types — unlike `source`, here aria-controls resolves to the real options container). `settlePoll` also excludes `selectedItemList` chips.
- **`is_required` detection varies by tenant.** Workday marks required fields with one of: `<abbr title="required">`, a **bare `<abbr>*</abbr>`** (asterisk as content, no title — US Bank dropdowns), `aria-required="true"`, or a label/legend whose visible text **ends with `*`**. Detect all of them (safe over-flag direction). Accuracy matters: a required field reading *false* is the dangerous direction — it hides an unfilled required field, and a required field the engine can't fill will block page advancement.

## Matching strategy

How a choice widget picks an option. Architectural decision, with rationale:
- **Value is an ordered candidate list, most-specific first**, supplied by the profile (`resolve()` coerces per widget type; an array passes through as a ready-made tiered list). The handler tries candidates in order. **A BOOLEAN profile value coerces to the tiered list `["Yes","True"]` / `["No","False"]` for dropdown/typeahead AND radio** (2026-07-23) — so a checkbox, a true/false dropdown, a yes/no dropdown, and yes/no radios all fill DETERMINISTICALLY from a stored boolean. *Why it matters:* a bare `"true"`/`"false"` string matched no "Yes"/"No" option and leaked required boolean questions (e.g. "Are you over 18?*") to the AI post-pass — flagged LEGALLY-LOADED on every fill despite the profile answering it. Both `resolve()` copies (lib.js/fill-driver.js + the background.js engine) are lockstep; regression-pinned.
- **Match ladder (per candidate, stop at first hit):** (1) **Exact** after `normalize()`; (2) **Containment — WIDGET-DEPENDENT, AMBIGUITY-SAFE + short-guarded** (`matchCandidates(cands, opts, {containment})`, default ON) — `startsWith` then `includes`, committed ONLY when **exactly one** option contains the candidate (a candidate in **2+ options is NOT a confident match** → skip), AND mid-string `includes` requires the candidate to be **≥ 3 chars** (a 2-char abbrev is a substring of too many unrelated options); (3) **Fuzzy ≥ 90** Levenshtein — **TYPO TOLERANCE ONLY**; (4) **Escalate** → `needs_review` (a REQUIRED field then goes to the AI rescue; optional → blank).
- **Containment is a GUESS unless Workday made it (2026-07-16). ApplyPilot never PICKS a containment match itself:**
  - **Dropdowns + radios (select from a full list)** pass `{containment:false}` → exact → typo → escalate. *Why:* a substring match on a shown list is a wrong guess (the `"PA"` → **"Armed Forces Pacific"** bug — `"pa"` ⊂ "pa**cific**", the ONLY option containing it, so the ambiguity guard couldn't help; it committed at `filled` with NO review flag). (`fillRadioCdp` was already exact-label-only, so this only changed `fillDropdownCdp`.)
  - **Typeahead / cert / source DIRECTED picks** (Workday showed a filtered list and did NOT autocommit, and we would click the one containing option) ALSO pass `{containment:false}` — same reasoning: us picking is a guess.
  - **Typeahead / cert / source AUTOCOMMIT recognition** KEEPS containment (default) — when *Workday itself* drops in a completed chip after you type (e.g. `"Training Instructor - AEVO"` → `"…AEVO - Multiple Recognized Providers"`), "the chip contains what I typed" is how we RECOGNIZE Workday's completion (vs a genuine stray like a `"Canada"` chip for a US query). That's trusting Workday, not guessing; still `filled_review` (flagged). The AI anti-hallucination belts keep containment too (the AI's choice → a real option; the AI rescue must succeed for required fields).
  - **ONE authorized exception — SKILLS (operator, 2026-08-07).** `matchSkillOption` has a **containment tier** so a skill Workday only lists under a broader name still lands (`Vivado` → `Xilinx Vivado`). It is safe only because of three guards, all earned on one live run: **WHOLE-WORD** containment (raw `includes` puts `Git` inside "Di**git**al" and `CAN` inside "**Can**adian"), a **distinctiveness gate** (a lone token must be ≥5 chars — on that run `CAN` was offered "**Can Openers**", a real whole-word hit the gate refused), and a **ranking tie-break** (several containing rows → Workday's own first result, alternatives named in the review). Every widened commit is `filled_review` + `skills-containment`, never silent. This does NOT relax the rule anywhere else.
  - **Net rule:** ApplyPilot accepts only an **exact** match, a **typo** (fuzzy ≥ 90), or a value **Workday autocommitted** — plus, for SKILLS only, a guarded **whole-word containment** (above). Everything else escalates → the operator picks it on the website review editor / teaches an answer bucket (→ an exact match next time), or the AI rescue fills a required field. **Lives in `matchCandidates` (lib.js + the inline `fillEngine` copy in `background.js` — LOCKSTEP); dropdown/radio + directed-typeahead call sites pass `{containment:false}`.**
- **Why not low-threshold fuzzy:** a 60% bar matches near-gibberish and silently selects a WRONG value, corrupting the application — the worst failure for an accuracy tool, worse than leaving a field unfilled. Fuzzy is typo-tolerance at 90+, not a general matcher.
- **`normalize()`** lowercases, strips a trailing `(+digits)`, collapses whitespace — lets "United States of America" exact-match the rendered "United States of America (+1)" with no fuzzy step. A tiered profile array (e.g. `["United States of America (+1)", "United States"]`) makes the exact-normalized hit land at **high** confidence instead of containment (medium).
- **needs-review / fuzzy connection:** a fuzzy/no match is not a confident answer — it's exactly the category that belongs in the human-review pile.
- **Parked (opt-in per field, never global):** dial-code-suffix matching ("any `(+1)` is acceptable for a US phone"). Global would silently accept a wrong country whose dial code happened to match.

## AI feature — multi-provider LLM (AI-0…AI-4 built)

Not-in-JSON questions (free-text/essays, unmapped choice fields, yes/no screening) leave REQUIRED fields empty → block Save & Continue → need an LLM. Built behind ONE provider-agnostic seam; **every AI fill is under the safety contract — guess + fill + FLAG `needs_review`, never silent trust — and the human review gate is the safety.**

- **The seam (`act.llm`, AI-0).** `llm.js` is the ONLY provider-aware code: `callLLM({provider, model, apiKey, system, user, maxTokens})` → normalized `{ok, text} | {ok:false, error}`, **NEVER throws** (Anthropic / Gemini / OpenAI builders+parsers; adding a provider = one entry). `LLM_MODELS` = curated per-provider model lists feeding the popup **dropdown** (default = the FIRST entry, single source of truth — **`gemini-3.1-flash-lite`** leads; a stale hardcoded model was the 429 lesson). `makeCdpActuation(llmConfig)` exposes `act.llm` (the only I/O method on `act`) + `act.aiEnabled` — both enforce the opt-in toggle (OFF ⇒ no provider call, no spend). The brain (fill-driver.js) builds the prompt + owns the decision, so it stays Node-testable with a fake `act.llm`. Popup config (provider/model/key + toggle + Test-connection); `manifest.json` host_permissions for the 3 hosts.
- **AI-1 — screening-question dropdowns (`aiFillField`, fill-driver.js).** A gated dispatch post-pass fires when `act.aiEnabled && f.isRequired && aiEligible(f) && producedNothing(record)` (an unmapped dropdown / genuine no-match). **ALWAYS-GUESS** — no UNKNOWN gate, because these are REQUIRED fields and a blank HALTS the walk: open → read the live options → `act.llm` with the profile + question + exact options → the model CHOOSES one + a SHORT justification that NAMES its basis (a positive profile fact vs reasoning-from-ABSENCE) + a confidence (High/Medium/Low). The choice is a **CANDIDATE that must clear the match ladder** vs the live options (never blind-commit) → text-keyed commit + read-back + persistence re-read. ALWAYS `filled_review`. `parseAiReply` tolerates ```-fenced / embedded JSON + a non-JSON fallback.
- **Safety / eligibility (HARD, unit-pinned).** AI-fill an unmapped/unmatched **dropdown / text / typeahead** — **but ONLY when the field is REQUIRED** (operator rule). An OPTIONAL unmapped dropdown/text/typeahead fills **deterministically only** and is left **BLANK** on a miss — a blank optional doesn't block Save & Continue, so there's no reason to spend an LLM call guessing it (INCLUDING optional EEO, incl. cascade-revealed Local-Name fields). The gate is `f.isRequired && aiEligible(f)` on `drivePageFill`'s INFER branch; `aiEligible` itself is a detector. The two value-CANONICALIZE paths (`aiCanonicalizeField` for a STATED dropdown value; the inline typeahead AI that only fires on a `resolve()`-produced candidate) are NOT gated — they operate on a value the user PROVIDED, not a guess, so they run for required OR optional. NEVER (regardless of required): `file_upload` and `checkbox`. A REQUIRED **radio** the deterministic pass can't answer now gets an AI guess via its OWN post-pass (`aiFillRadio` — NOT through `aiEligible`, mirroring the typeahead pass): infer from the profile → the pick clears the match ladder vs the live labels → commit via `fillRadioCdp` → ALWAYS `filled_review`, flagged HARD, never blank-blocking. This INCLUDES `candidateIsPreviousWorker` when its employer-match path is UNEVALUABLE (no company set + no known employer named) — the **safety reversal**: AI-guess to REACH review (force-flagged `ai-choice-sensitive` → LEGALLY-LOADED; a low-confidence guess auto-escalates to super-hard in the viewer) rather than leave a truthfulness-adjacent required field blank. GATED on `record.resolved == null` so a decided-but-uncommitted employer-match answer (e.g. a matched "Yes") is NEVER overridden by a contradictory guess. AI OFF / OPTIONAL radio ⇒ stays blank (unit-pinned). **EEO/protected (gender/race/ethnicity/veteran/disability/sexual-orientation) is NO LONGER excluded for REQUIRED fields — the operator RETRACTED that rule: a REQUIRED EEO field fills via the SAME AI inference as any required field, then gets the loud `ai-eeo-guess` "AI-GUESSED DEMOGRAPHIC — VERIFY" review badge (re-tagged at the call site; `isEeoField` is a detector, not a blocker). An OPTIONAL EEO field is left BLANK (the optional gate above — uniform). A STATED demographic still fills deterministically — the AI never overrides a value you provided.** Toggle OFF ⇒ `act.llm` never called. `legallyLoaded(label)` (widened to catch "over the age of 18") → `ai-choice-sensitive`.
- **The no-commit dismissal (`closeAndVerifyBlank`).** The UNKNOWN/no-match path must leave the field BLANK — and **blank is VALUE-based** (`triggerText` stayed on the opening placeholder), NOT the listbox state: a STRAY commits a value (which ALSO closes the list), so the value-check is the real property; a genuinely CHANGED value is surfaced (`*-stray`), never a false "blank, please answer." (An `ariaExpanded` hard-gate + a reopen-toggle once manufactured a false stray on a slow-closing list — both removed.) This is the SOLE guard on the no-commit path (the M40 audit only re-reads `filled`/`filled_review`, never a blank field). Reused by the recon (`reconDropdownDump`).
- **The review gate bites (two operator requirements).** `flag` is persisted in the bundle; `deriveConfidence` surfaces the AI's self-reported confidence (`confidence_source:"ai_inference"`); the viewer (`summary.js`) renders **`ai-choice-sensitive` answers FIRST with a red "⚠ LEGALLY-LOADED — VERIFY" badge — prominence off the FLAG, never confidence** (a high-confidence reasoning-from-absence answer, e.g. criminal→"No", must NOT be the easiest to scroll past) + the AI-INFERRED badge + the justification (which names its basis). The super-hard tier (`ai-closest-forced` + low-confidence AI) renders loudest, FIRST. M40 audit re-reads AI fills.
- **AI prompts pass the STATED answer (the candidates), NOT the whole profile**, when one exists (`statedAnswerBlock`) — saves tokens + matches a typo ("Otherrr"→"Other") instead of inferring an unrelated profile fact; falls back to the profile only when there is no stated answer (e.g. EEO).
- **Recon harness** (`reconDropdownDump` + `RUN_CDP_QUESTIONS_RECON` + `cdp-questions-recon`): read-only dump of a screening page's dropdowns (verbatim labels + options + a verified-blank clean-close) — the new-tenant probe before relying on the fill path.
- **Status:** AI-0 (adapter), AI-1 (screening choice), the inline typeahead/tree rescues, and AI-4 (remediation — see Multi-page) are live-verified. AI-2 (essays — the required-text INFER branch) and the AI-3 EEO corner (`aiInferEeoField`, kept only for the mapped-but-empty REQUIRED EEO dropdown) are built, live-verify pending. Deferred enhancements: see Current state & open items.

## Answer buckets (website-driven; Profile v2)

The website (`WEBSITE.md`) owns a `buckets_json` store synced via `AP_SYNC_PROFILE`. A **bucket** = one
canonical answer + the question wordings that map to it. The extension consults them in `drivePageFill`
for any UNMAPPED field the deterministic pass left empty, **before** the AI post-pass:
- `buildBucketIndex(buckets)` builds normalized-wording → bucket (`apMatch.normalizeLabel`, LOCKSTEP with
  the website's `normalizeQuestion`). **Exact-normalized match only — no fuzzy** (the AI fallback covers
  misses; a fuzzy tier would only add silent-wrong-match risk).
- `fillFromBucket`: **Mode A** (`profile_path`) resolves the bound profile value; **Mode B** uses the
  bucket's own `value` — a **CANDIDATE LIST** (`string[]`, a legacy string tolerated): text → `value[0]`,
  choice widgets pass the whole list through the match ladder (fills like a tiered dropdown/typeahead
  across tenants). Either way it's a CANDIDATE through the SAME match ladder vs the LIVE options — never a
  blind commit; a no-match falls through to AI/blank. A real commit is flagged `bucket` (a "remembered"-
  style provenance, NOT an `ai-*` flag). Gated `producedNothing(record) && !mappedPath` (a mapped-but-no-
  match field goes to CANONICALIZE instead). Runs for REQUIRED **and** OPTIONAL fields.
- The SW loads `buckets` from `chrome.storage.local` and hands them into `drivePageFill` (engine computes /
  SW does I/O). Unit-pinned in `test/fill-driver.test.js` (fake bucket: Mode A/B, candidate-list + legacy
  string, match-ladder gate, runs-before-AI, `buildBucketIndex` normalization). **Supersedes** `answerBank`.
- **Teach-flow piggyback (for the website `/app/teach` page).** The AI fill functions
  (`aiFillField`/`aiFillText`/`aiFillRadio`) return, in the SAME fill call, `maps_to` (the profile field
  this question maps to; `""`=none) + `suggested_category`; these ride each review-bundle entry (`buildReviewBundle`
  + `background.js buildEntry`, lockstep). The website teach page consumes them so curation needs **no extra
  LLM call** for AI-filled questions. Buckets match LABEL-only (`normalizeLabel`); `bucket.selectors`
  (per-platform ids) stays UNUSED scaffolding. `normalize`-style lockstep dup: `normalizeLabel` (lib.js) ↔
  `normalizeQuestion` (web `lib/buckets.ts`). Not-yet-wired: date/textarea bucket **filling**.
- **Answer ladders are SEPARATE from the question bucket (2026-07-23).** The **bucket** = the question
  WORDINGS that map to a field; the **answer ladder** = the acceptable ANSWER variants for that field. They
  are two different things (modeled on Country's tiered list). `answer_ladders: Record<path, {yes:string[],
  no:string[], values?:string[]}>` lives in `profile_json` (**no migration** — rides the profile blob);
  `yes`/`no` = triBool polarity ladders, `values` = scalar variants. UI: the profile page shows an in-field
  `›` arrow → `AdvancedChoices` popup on EVERY `TextField`/`SelectField` (proactive — pre-load variants
  like GPA `["4.0/4.0","3.5+"]` WITHOUT waiting for a teach); the teach page shows the same popup on
  clicking the answer. Fill: `appendFieldVariants`/`boolLadderCandidates` (fill-driver.js) append the
  ladder's variants as extra match-ladder candidates for choice widgets, keyed by the bucket's
  `profile_path` VERBATIM (dotted, incl. numeric `education.0.gpa`).
- **Buckets fill REPEATING-section entries too (2026-07-25, operator's design).** Inside a repeating
  section every entry shows the SAME wording, so the bucket identifies **which FIELD** and the entry
  **ORDINAL** picks **which VALUE**: a bucket bound to `education.0.school_or_university` fills entry 0
  from `education[0]` and entry 1 from `education[1]` (the value is read from the ENTRY'S OWN item — no
  index remapping). Runs in `fillEntryCdp` AFTER the fieldMap loop, ONLY for entry fields the map did not
  claim (id or label), so it can never double-fill; the bucket's path ROOT must name the section
  (`itemsKey`) or it can't fire; and when a bucket fills a field the map named but couldn't RESOLVE, it
  updates that record instead of duplicating it. **Mode B (a fixed `value`) does NOT fire per-entry** —
  with no indexed data, filling every entry identically is a guess. Same safety as the flat tier: a
  CANDIDATE through the match ladder, flagged `bucket`, never a blind commit. Unit-pinned.
- **Every profile field's bucket ships with the field's OWN NAME as a default wording (2026-07-26).** The website's `ensureDefaultFieldWordings(buckets, profile)` (web `lib/teach.ts`, applied on LOAD next to `ensureStarterBuckets` at the sync slice / teach API / profile editor) seeds a Mode-A bucket per profile field with its humanized label — the first-name bucket contains "First Name" — so a form that labels its question the way the profile labels the field fills deterministically even when the tenant's automation-id isn't in `FIELD_MAP`. Matching is normalized, so casing and spacing don't matter. Non-destructive + idempotent (operator wordings kept, dedup by `normalizeQuestion`). SKIPS labels too generic to be a safe EXACT match (type/name/value/url/id/status/title/other/notes/description) and every repeating entry past the PRIMARY one. **WEBSITES are the exception both ways:** each entry is a DIFFERENT question, so EVERY entry gets a bucket and the wording is the entry's TYPE verbatim — "LinkedIn", "GitHub", "Personal Website" (never "URL"). Website URLs are stored as the FULL CANONICAL link — scheme **and `www.`** (`websiteSchema.url` transforms through `ensureHttpsUrl`, LOCKSTEP with the extension's `ensureHttps`), so the value seen, synced and filled is one string. **Why `www` is REQUIRED (2026-07-26):** the site/form canonicalize to the www host, and a bare-host profile value then fails EVERY equality tier — exact, containment (`www.` is inserted MID-string, so neither side contains the other), and fuzzy (**89** vs the 90 bar) — which flags the M40 audit (`textValuesMatch` has phone-digit relief only) and makes `submitPrecondition` BLOCK on a review-page DISAGREE. `www.` is added ONLY to a bare APEX host (2 labels, or 3 ending in a multi-part public suffix like `co.uk`); a host that already carries any subdomain (incl. `www.`), an IP, or userinfo is returned UNTOUCHED — inventing `www.blog.example.com` would break a working link, a worse failure than the mismatch. ## Employer match — "previously employed here?" (safety-critical)

`candidateIsPreviousWorker` sits next to a **truthfulness certification**, and selecting "Yes" unfurls follow-up fields — so a wrong "Yes" is a false legal statement. `decidePreviousWorker(company, questionText, employers)`:
- **clean miss** (no known employer matches) → fill **"No"**, no review (confident non-membership). A **complete (non-empty) list makes this safe WITHOUT a company anchor** (operator 2026-07-24: "trust your list") — a clean miss fills "No" even when `jobContext.company` is unset; the anchor only corroborates the Yes/overlap paths.
- **partial overlap** with the application company → fill **"No" + review** (name overlap may be the same employer).
- **exact company match OR a known employer named in the question text** → fill **"Yes" + review**.
- **unevaluable** (list unconfigured / `[]` — an empty list can't confirm non-membership) → **blank + review** — no blind guess. (No longer "no company set": a non-empty list fills "No" without the anchor.)
- **NEVER auto-"Yes" without a review flag.** *Why:* this field is adjacent to a truthfulness certification and a "Yes" unfurls follow-up questions, so a wrong positive is a false legal statement — every "Yes" (and every uncertain "No") gets a mandatory human check, never a silent auto-answer.
- **Question-text scan:** these questions name the entities that count (affiliates/subsidiaries/predecessors — "Elavon, U.S. Bancorp Investments, Union Bank"; "Ken Garff") which the bare `jobContext.company` misses. Scan the question label for each known employer via a **contiguous whole-word token-sequence** match, gated by a distinctiveness check (multi-word, or a lone word ≥5 chars not in `GENERIC_SINGLE`) so a short/common entry ("Bank") can't false-match boilerplate. Works even with `jobContext.company` unset (adds a "no company to corroborate" note). It reads the user's KNOWN employers out of the question — it does NOT extract company names from prose (no LLM).
- **`employment_history_companies` = industry employers ONLY** (companies you were formally employed by; excludes academic/lab/club affiliations). Its completeness is what makes the auto-"No" safe. `["none"]` = "never formally employed" → confident "No"; `[]` = unfilled → flags every such question for review.
- **Custom employment-status screening questions fill DETERMINISTICALLY on EVERY widget type (no AI, no flag) — 2026-07-24.** A tenant's OWN worded yes/no question ("Are you a former MAGNA employee?", "Are you currently employed with Magna?", the checkbox assertion "I am a former Magna employee") is NOT Workday's standard `candidateIsPreviousWorker` field, so it used to fall to the AI fallback → force-flagged `ai-choice-sensitive` (the "LEGALLY-LOADED — VERIFY" badge) on every fill despite being answerable from the profile. Now a **deterministic recognizer** (`recognizeEmploymentQuestion`, fill-driver.js — a post-pass AFTER the bucket consult and **BEFORE the AI FALLBACK block** (placement is load-bearing: the dropdown/text AI would otherwise fill it first); a DETERMINISTIC tier like buckets → runs for REQUIRED **and OPTIONAL** fields, the AI fallbacks stay required-only) fires when a yes/no-capable widget — **radio, dropdown, text/textarea, checkbox** — meets ALL of: (a) one SENTENCE **names the application company** (`jobContext.company`) with an employment word within 3 tokens (or "worked/working for/at/with «co»" — bare "work" deliberately excluded), (b) that sentence **asks about YOU** (`EMPLOY_ASK_RE`: "are/were/have/do/if you … employee/employed/worked", the FIRST-person checkbox assertion "I am/was a «co» employee", a terse "Former «co» employee?" opener, or "your former/current employer"), and (c) **no BAIL pattern** hits (`EMPLOY_BAIL_RE` — hardened 2026-07-24 against adversarial wordings that WOULD produce a silent wrong answer: wrong SUBJECT "relatives/spouse/referred-by/know-anyone employed at «co»"; wrong OBJECT/scope "employed by a competitor/supplier of «co»", "terminated by ANY employer"; different FACT "eligible/authorized for employment" (work-auth!), termination manner, reference-contact, policy/handbook consent; inverted POLARITY "I certify I am not…", "are you not/no longer" — while the Magna conditional "If you are not a former MAGNA employee, please select No" is EXEMPTED by its same-sentence select-instruction; ASPIRATIONAL "would you accept/interested in/able to begin employment"). Sentence scoping kills cross-sentence contamination ("Do you have a criminal record? Magna requires all employees…"). Tense: current-only → `decideCurrentlyEmployed` (derived from the work-history `currently_work_here` flags); former/ever → the existing `decidePreviousWorker`; **BOTH ("current or former") → "ever"**. The decision maps to the live option by **leading-token polarity** (`optionForPolarity` — exact first, else a UNIQUE Yes/No-leading label like "No, I'm NOT currently employed with Magna"; 2+ leading → refuse → AI) and commits per widget: radio via `fillRadioCdp`; dropdown via `openAndReadDropdown` + the AI path's text-keyed click + persistence re-read (prefilled-equal → kept, ZERO value actuation); **text/textarea** type the polarity word via `fillTextCdp` — EXCEPT a detail-REQUEST field ("please enter/list/provide your employee ID/dates…"), which is NOT a yes/no ask → left for AI-2 (a bare silent "No" there would be sloppy); **checkbox**: a REQUIRED checkbox is STILL always auto-checked (operator rule 2026-07-24 — required can't stay blank), but a grounded-"No" CONTRADICTION re-flags the check `filled_review`+`employer-match` (never silently assert what the profile contradicts; agreement/unevaluable → silent as before, ordinary consents unchanged — their agree/authorize wording bails the recognizer); an OPTIONAL checkbox is DETERMINED — check="Yes" (always review), uncheck="No" (virgin box → zero actuation, silent; clearing a pre-ticked box → forced review). A clean **"No" fills SILENTLY** (status `filled`, no flag — a grounded fact from your complete list, NOT absence-reasoning); a **"Yes"/uncertain → `filled_review` + `employer-match`** (renders `employer_match_uncertain`, NOT AI-inferred; **never auto-"Yes"**); a **pre-existing DIFFERENT real value is never silently overwritten** (commit + forced review). Unrecognized / unevaluable / polarity-unmappable → the AI/blank fallback unchanged; a commit-fail sets `resolved` so `producedNothing` stays false and the AI can never override a made decision. **Anchoring uses `empCompany` = `jobContext.company` (scraped) OR the page URL's TENANT SUBDOMAIN** (`tenantCompanyFromUrl`, lib.js — `magna.wd…myworkday{jobs,site}.com` → "Magna"; Option 1, 2026-07-25). The tenant is always present in the URL, so the recognizer/employer-match never fall to the AI just because the scrape/hand-off didn't populate a company; computed ONCE at the top of `drivePageFill` from `scan.url` and used at every employment site (candidateIsPreviousWorker + the recognizer post-pass + the checkbox contradiction flag). The recognizer still confirms the company is NAMED in the question; the answer comes from your employer list. `jobContext.company` (from the JD scrape) is now an optional override + display only. Operator decisions (2026-07-24): a **non-empty** employer list is treated as complete; current employment derives from the work-history flags; a clean miss is always "No" even when the question broadens to affiliates/subsidiaries (we trust your list — there is no ownership DB). Lives in fill-driver.js (CDP path); adversarial wordings unit-pinned in `test/fill-driver.test.js`.

## Review summary (the fill → review → submit contract)

**PRIMARY review surface = the WEBSITE now (2026-07-16).** The human edit/approve stage was ported to the site (`WEBSITE.md` M9: `components/app/review/ReviewEditor.tsx` over the same `reviewSummary` schema; pure transforms `web/lib/review-approval.ts` — a LOCKSTEP port of `summary-lib.js` — + `web/lib/review-model.ts` port of this `summary.js`'s grouping). Round-trip: the walk PUSHES its accumulated bundle to the site on every exit (`reportApplication` in `runCdpWalk`'s finally); before replay the SW PULLS the site-approved bundle (`pullApprovedBundle` → `GET /api/extension/review`, writing `chrome.storage.local.reviewSummary`) so `runCdpReplayWalk`/`submitPrecondition` are UNCHANGED (site connected + has a bundle ⇒ it's the source of truth). **The pull MUST be TARGETED for a submit run (2026-07-26).** By default it keys on the LOCAL bundle's url, and the endpoint's no-match fallback is "the most-recently-updated app that HAS a bundle" — so submitting job B while storage held job A's fill would have replayed **A's approved values into B's form and submitted it**. The extension's own `summary.html`/`summary.js` viewer/editor (below) STAYS as a fallback for when the site isn't connected, until the web path is live-verified — keep the two schemas in lockstep.

## Resume upload & storage

The resume is NOT picked from the OS filesystem per application. *Why:* the end state generates a per-application AI-tailored resume variant (or one fixed resume), so the bytes are held/produced inside the extension and attached programmatically — a picker is incompatible with generated variants and hostile to the high-volume queue-and-run premise.

- **Storage (`db.js`):** one PDF uploaded in the popup → **base64 in IndexedDB** (DB `ApplyPilot`, store `resume`, single fixed key **`resume:default`** → `{filename, mime, size, base64, savedAt}`). IndexedDB, not `chrome.storage` — a real resume's base64 blows past its quotas and binary document bytes don't belong there. `db.js` loads in three contexts off ONE file (popup `<script>`, SW `importScripts`, Node `require` — UMD-lite), which makes it unit-testable (fake-indexeddb). **Phase 2+ (AI-tailored per-application variants) just adds more keys to this same store — do NOT pre-build variant slots or per-application keying.**
- **Attach (`attachResume`, self-contained):** **strings only across the injection/message boundary — a `File`/`Blob` serializes to `{}`.** The SW reads the base64 from IndexedDB and passes it as plain STRING args; the injected fn rebuilds the `File` in the page, sets `input.files` via a `DataTransfer`, and dispatches `change` (Workday's delegated React `onChange` fires). It first **clears existing attachments** one-at-a-time, **re-resolving the section/items/`delete-file` fresh from `document` each pass** — Workday swaps the subtree mid-loop, so a captured ref goes stale and caps deletion at n−1.
- **Success = the confirmation ROW, not the input:** `input.files` RESETS to 0 after Workday's XHR upload. Gate specifically on **`file-upload-successful`** (`file-upload-item` renders first, before the success marker).
- **`role="alert"` on the upload widget is the STATUS channel, NOT an error channel (2026-07-29).** Workday announces upload PROGRESS there — live: `"Kevin's Hardware Resume.pdf loading"`. A first cut of the error detection matched any `[role="alert"]` text and reported *"Workday reported an upload error"* on a perfectly healthy in-flight upload, which then made the SW **skip the very re-poll** that exists for a slow upload → a false `resume-not-attached` HALT on a rehearse run. (dom-patterns already recorded this channel announcing "…successfully uploaded", and `expandErrorSamples` already drops role=alert toasts for the same reason — the precedent was there.) Now: the text is read as a **`statusText`**, an ERROR requires unambiguous wording (`error|failed|unsupported|too large|invalid|not allowed|try again`) or a dedicated `file-upload-error` node, and **progress wording (`loading|uploading|in progress|processing|N%`) is POSITIVE evidence the upload is still in flight** — it sets `uploading`, which *extends* the SW re-poll (45s instead of 20s) instead of aborting it. The re-poll also re-reads the status each tick so a genuinely LATE error stops the wait. Every failure path now logs `cleared/deleted/filesSet/sawItem/uploading/status`. **Why the REPLAY run hits this and the FILL run doesn't (leading suspect, not yet confirmed):** a fill lands on a virgin Documents section so the clear loop is a no-op, whereas a re-apply finds Workday's carried-over copy and must delete-then-re-upload — a slower server round trip right before the upload. The new `cleared=/deleted=` log settles it on the next occurrence.
- **The confirmation wait is VISIBILITY-SCALED + RE-POLLED FROM THE SW (`cdpAttachResumeConfirmed`, 2026-07-28).** `attachResume`'s gate is a PAGE-side poll, so a hidden tab subjects it to a slower XHR, a throttled React render, and (when CSP blocks the worker-timer override) ~1Hz timers. Live on a BACKGROUND run it reported *"file-upload-item appeared but file-upload-successful did not within 10s"* and the replay walk HALTED `resume-not-attached` — while the same job attached fine on later runs, the signature of a race, not a broken upload. Now: the page-side ceiling is a PARAMETER (VISIBLE 10s — the live-verified value, unchanged; HIDDEN 25s), and an upload that STARTED but hasn't confirmed is then re-polled **from the service worker on wall-clock for 20s more**, waking the page each tick (the standing rule that a wait must never depend on a page timer). An explicit Workday error row (`errorText`) or an upload that never started SKIPS the re-poll — those aren't races, and waiting would only delay an honest failure. ONE shared path for both walks (the fill's `fillAndPersistPage` block and the replay's `replayAttachResume`); it also owns the `__apActing` bump.
- **Wiring:** page path = the SW post-fill step `attachResumeForPage` (both `RUN_FILL` and the walk). CDP path = `cdpEval(attachResume, …)` on the SAME debugger attach, inside `fillAndPersistPage` (after `drivePageFill`, before the bundle build), patching the `file_upload` record to `filled`; no-resume / failed attach → `needs_review` and the walk halts `resume-not-attached` BEFORE clicking Next (self-explaining, not a bare nav-timeout). The attach bumps `window.__apActing` so the input-lock doesn't swallow its synthetic delete-clicks. Per-entry attachments (e.g. per-cert) are the operator's job (form / review picker) — the résumé only ever attaches to the top-level Documents field (regression-pinned). ## Workday never rewrites a committed value into a DIFFERENT option (operator, 2026-08-06)

**A committed value can, very rarely, be REMOVED by Workday. It is NEVER silently changed into another
option.** So when a field you committed later holds a *different* valid option, that is **us**, not the
tenant — stop looking for an explanation on Workday's side and go find our own stray write.

This is a load-bearing diagnostic rule, and ignoring it cost a full debugging round. Live on waystar
page 3: relocation was committed `"Yes, I am open to relocating"` and later read `"No, but I live near
one of these locations"`. That was written up as "Workday rewrites the value on its own", and the
remedies built on that premise (answer memory, a pre-Save recovery) treated a symptom. The real cause
was ours: **every portaled listbox renders at the SAME screen coordinates** (every commit on that page
logged `rect=463,298`), the options **linger a beat while unmounting and stay clickable**, and the next
field's open-click therefore landed on the previous field's still-mounted list — selecting the option
that happened to sit at that point. Changing relocation then remounted the dependent basecamp question
under a new automation-id, blank and required, which is what blocked Save.

`closeDropdownConfirmed` has gated the DETERMINISTIC path on options-GONE (not merely `aria-expanded`)
since 2026-07-06; the **AI commit paths never called it**, and they are what fill screening questions.
Now gated: `aiFillField`, `aiCanonicalizeField`, and the employment-status dropdown commit.

Corollary for triage: value GONE ⇒ plausibly Workday (rare). Value CHANGED to another real option ⇒
ours — look for a lingering list, a stale rect, or a second write, in that order.

## Working principles

- **`apMatch` is TWO objects — Node gets all of lib.js, the SW gets a HAND-WRITTEN literal.** `fill-driver.js` reaches lib.js through `apMatch`, which is `require("./lib.js")` under Node but an explicit object literal in the service worker. So `apMatch.foo(...)` can pass every test and throw `apMatch.foo is not a function` in the browser — live 2026-07-28, the replay walk died mid-run on `apMatch.dateOrderOf` after the collision fix routed the call sites through it. **Adding a lib.js helper that fill-driver uses means updating BOTH: lib.js's `module.exports` AND the SW literal.** Guarded by `test/sw-globals.test.js` (every `apMatch.X` used must be in the literal, and every literal key must be exported by lib.js — both verified to FAIL when broken).
- **ONE global scope in the service worker — never re-declare an imported name.** `background.js` loads db/lib/llm/gmail/cdp/fill-driver with `importScripts`, which evaluates them all into the SAME global scope (unlike Node's per-module scope). Two files declaring the same TOP-LEVEL name is a `SyntaxError` and the worker **fails to register at all** — "Service worker registration failed. Status code: 15", i.e. a completely dead extension. It happened live (2026-07-28): `dateOrderOf` moved into lib.js and a one-line alias was left in fill-driver.js so its call sites wouldn't change; **all 765 node tests stayed green** because Node never shares a scope, and only loading the unpacked extension surfaced it. fill-driver.js reaches lib.js helpers via **`apMatch.*`** — that indirection is exactly why the two files can coexist. Guarded by `test/sw-globals.test.js` (it derives the file list from the real `importScripts` call, and is verified to FAIL if the collision is reintroduced); deliberate lockstep dups live INSIDE functions, so they never touch the global scope.


- **Trace the real DOM before writing a handler — don't guess.** Every hard bug (the `source` picker, the dropdown chip contamination) only cracked after blind guesses failed and we instrumented a read-only trace of the *actual* DOM, then built from what it showed. Guessing widget shapes wasted rounds; tracing settled them — make a discovery trace the first step on any new widget/tenant.
- **Incremental:** one focused change per milestone, verified on a real page. No skipping ahead.
- **Observation-driven:** rules in `docs/dom-patterns.md` come from observed DOM, not assumptions; keep code and doc in sync.
- **Don't port the Python repo blindly:** it's a design reference (intent, prompts, edge cases), not code to mechanically translate to JS.
- **Commit per milestone:** each working milestone gets a commit, so we can bisect when something breaks.
- **Keep this file lean:** standing rules and invariants only. When a milestone lands, update the relevant rule section here (a few lines) and append the full dated entry to `docs/progress-log.md`; observed-DOM findings go to `docs/dom-patterns.md`.
- **Three consoles:** service worker (`background.js` + the engine's returned data), page F12 (anything `console.log`'d inside the injected function), popup right-click → Inspect (`popup.js`). Most `[ApplyPilot]` output is in the service-worker console.
