# ApplyPilot Chrome Extension

## What this is

A Manifest V3 Chrome extension that automates Workday job applications from a stored profile. From-scratch rewrite of a Python + Playwright tool of the same name; the Python repo lives separately and is a **design reference, not code to port** — it documents what the system should do; this repo builds it for the runtime that will ship. The shape is a **fill → review → submit** pipeline: the engine fills a page and produces a per-field review summary, a human reviews/edits it, and a later pass replays the approved values (submit half not built yet).

## Architecture & invariants

- Manifest V3; host permissions `*://*.myworkdayjobs.com/*`.
- **Active-tab injection — NOT a content script, NOT a background tab.** `background.js` (service worker) receives a `RUN_FILL` message from the popup and uses `chrome.scripting.executeScript` to inject `fillEngine` into the active tab (frame 0). *Why:* the operator is logged in and on the form themselves, so injecting into the active tab fills the page they're looking at. Content-script files and background-tab/multi-page automation were deliberately deferred — not needed for active-tab fill.
- **Profile + defaults + jobContext live in `chrome.storage.local`** — the permanent website→extension handoff contract. The engine ALWAYS reads them from storage (today the popup's "Load default profile" seeds `profile` from `data/profile.json` and `defaults` from `data/application_defaults.json`; `jobContext.company` is set via a popup field; later a website will write them). The engine is agnostic to how they got there.
- **"Engine computes / service worker does I/O."** The injected `fillEngine` is self-contained (closes over nothing from the SW), reads/writes the page DOM, and RETURNS results — it never touches `chrome.storage`. `background.js` does all storage I/O (e.g. persisting the review summary). Keep this boundary.
- **Pipeline shape:** fill (engine, per page) → review (the `reviewSummary` + `summary.html` viewer/editor, human edits) → submit (replay approved values; not built).
- **UI:** `popup.html`/`popup.js` — buttons **Load default profile**, **Fill current page**, **View last summary**, **Set company** (temporary jobContext entry), plus **CDP recon** / **CDP fill (hidden)** (M24 — see CDP off-loop actuation). `summary.html`/`summary.js` — the review-summary viewer/editor. `[ApplyPilot]` logs land in the **service-worker** console (see Working principles → three consoles).

## Workday DOM model

See `docs/dom-patterns.md` for the full, dated rulebook (every observed tenant + refutations). Short version:
- Every form field sits in a `<div data-automation-id="formField-*">` wrapper.
- `classifyField` derives the widget type from wrapper descendants, first match wins: **hierarchical `source` → typeahead (`data-uxi-widget-type="multiselect"`) → radio (`input[type=radio]`) → dropdown (`button[aria-haspopup="listbox"]`) → checkbox → text → unknown**.
- **Rules come from observed DOM, not the Python spec.** Patterns the spec assumed do NOT hold on observed pages (e.g. `role="combobox"`, `role="radiogroup"` don't fire on Comcast). When code and doc disagree, fix one — don't let them drift.

## React fill technique

Workday is React-based: `input.value = "x"` updates the DOM but not React's internal state, so the value reverts on submit. The working pattern (verified on Comcast text fields; needed for any controlled input):
1. native setter: `Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype, 'value').set`
2. `nativeSetter.call(input, value)`
3. dispatch `new Event('input', { bubbles: true })`
4. dispatch `new Event('change', { bubbles: true })`

## Interaction patterns (the shared helpers)

Primitives proven against real Workday pages, now the shared helpers inside `fillEngine` (`background.js`). Reuse them — don't reinvent.

- **`robustClick` — the click primitive.** Three-strategy ladder: (1) pointer-event sequence (`pointerdown→mousedown→pointerup→mouseup→click`, `clientX/Y` from the bounding rect — closest analog to a real click), (2) native `el.click()`, (3) bare `MouseEvent('click')`. On Comcast the pointer sequence has succeeded on every widget; the fallbacks are kept because portaled-listbox/overlay layers can mask synthetic clicks on other tenants. Use it for any non-text-input interaction.
- **Typeahead is open-before-find.** The searchBox `<input>` isn't reachable until the widget opens (container carries `data-automation-hiddensearch="true"`). Click the opener first, then `waitFor` `input[data-automation-id="searchBox"]` scoped to the wrapper. Opener ladder: `[data-automation-id="multiselectInputContainer"]` → `[data-uxi-widget-type="selectinput"]` → first `<input>` → wrapper.
- **Clear before typing.** Set the search input to `""` (native setter + input event), wait briefly, then type — avoids residual-text contamination on re-fill.
- **Settle-poll the filter, don't scrape on a fixed delay.** Live-filtering typeaheads race a fixed `setTimeout` (we saw option counts flip 21↔1 with wrong matches). Poll the enabled-option count ~120ms and accept only after **two consecutive equal, non-zero reads**, with a timeout fallback to the latest read.
- **Sequential cleanup — don't over-engineer per-field close.** Moving to the next field blurs the prior widget and dismisses its listbox for free. We burned time on explicit Escape/click-outside closes before realizing the sequence handles teardown. Per-field handlers focus on open+select; only the last field could leave a listbox open (cosmetic).
- **Radios: click the label, group by `name`.** Inputs are CSS-clipped; the `<label for="<id>">` is the styled click target (native label-activation flips `checked` + fires the change event React listens for). Group by shared `name` (not a `role="radiogroup"` wrapper, which Comcast omits). Verify via `input.checked`.
- **Options are portaled to the document root** (outside the `formField-*` subtree). **But a bare page-wide `[role="option"]` scrape is contaminated** — scope dropdown scrapes to the field's own listbox (see DOM lessons → chip contamination + aria-controls scoping). Filter `aria-disabled="true"` (the "Select One" placeholder).
- **Always verify state, not just click outcome.** `robustClick` returning a strategy means an event fired, not that the page updated. Re-read observable state after a delay: radios → `input.checked`; dropdowns → trigger text; typeaheads/source → the `selectedItem` chip / `multiselectlistitem` selected-state. Synthetic clicks have no-op'd silently.

## Choice-widget handlers & hard-won DOM lessons

These cost multiple rounds; full per-tenant detail is in `docs/dom-patterns.md`. The load-bearing whys:

- **`source` ("How did you hear about us?") has three tenant shapes**, all handled by `fillSource` (discover-and-trace): Cambium = button+listbox **expand-walk** (no searchBox); Comcast = typeahead; **US Bank = searchBox that filters on ENTER, not live**, whose result leaves are `<div data-automation-id="promptOption" data-automation-label="…">` — **NOT `role="option"`** (that role is on a sibling `menuItem`), and whose searchBox `aria-controls` points at a `promptAriaInstruction` node (the wrong target). So: type → full Enter → race-safe wait for `promptOption`s → match on `data-automation-label` → click → **commit-gated** via the enclosing `multiselectlistitem` selected-state (so no false "filled").
- **Dropdown option contamination — and why visibility filtering is a DEAD END.** A page-wide `[role="option"]` scrape pulled in two *genuinely-visible* contaminants: (1) **selected-item CHIPS** — a filled multiselect/source renders its selected value as `<ul role="listbox" data-automation-id="selectedItemList"><li role="option" data-automation-id="selectedItem">…</li></ul>`, i.e. **the chips carry `role="option"` markup**, so "LinkedIn"/"(+1)" showed up as options inside every dropdown; and (2) **a prior dropdown's listbox stays open** (filling State, Country's `ctny0` was still mounted, so State listed countries). **Visibility filtering was tried TWICE and confirmed a dead end — do not retry it**: both contaminants are genuinely `visible:true` (the chips are shown; the prior listbox is still open), so a visibility filter can never remove them. **Fix:** scope the scrape to the trigger's own `aria-controls` listbox (verified per widget: `ctny0`→countries, `ctny1`→states, `ctny2`→phone-types — unlike `source`, here aria-controls resolves to the real options container). `settlePoll` also excludes `selectedItemList` chips.
- **`is_required` detection varies by tenant.** Workday marks required fields with one of: `<abbr title="required">`, a **bare `<abbr>*</abbr>`** (asterisk as content, no title — US Bank dropdowns), `aria-required="true"`, or a label/legend whose visible text **ends with `*`**. Detect all of them (safe over-flag direction). Accuracy matters: a required field reading *false* is the dangerous direction — it hides an unfilled required field, and (multi-page round) a required field the engine can't fill will block page advancement.

## Matching strategy

How a choice widget picks an option. Architectural decision, with rationale:
- **Value is an ordered candidate list, most-specific first**, supplied by the profile (`resolve()` coerces per widget type; an array passes through as a ready-made tiered list — M13.2). The handler tries candidates in order.
- **Match ladder (per candidate, stop at first hit):** (1) **Exact** after `normalize()`; (2) **Containment** — `startsWith` then `includes`; (3) **Fuzzy ≥ 90** Levenshtein — **TYPO TOLERANCE ONLY**; (4) **Escalate** → `needs_review` rather than guess.
- **Why not low-threshold fuzzy:** a 60% bar matches near-gibberish and silently selects a WRONG value, corrupting the application — the worst failure for an accuracy tool, worse than leaving a field unfilled. Fuzzy is typo-tolerance at 90+, not a general matcher.
- **`normalize()`** lowercases, strips a trailing `(+digits)`, collapses whitespace — lets "United States of America" exact-match the rendered "United States of America (+1)" with no fuzzy step. A tiered profile array (e.g. `["United States of America (+1)", "United States"]`) makes the exact-normalized hit land at **high** confidence instead of containment (medium).
- **needs-review / fuzzy connection:** a fuzzy/no match is not a confident answer — it's exactly the category that belongs in the human-review pile (later: an LLM-judge call).
- **Parked (opt-in per field, never global):** dial-code-suffix matching ("any `(+1)` is acceptable for a US phone"). Global would silently accept a wrong country whose dial code happened to match.

## Deferred LLM roadmap (where the LLM grows in, and why not yet)

Two matching jobs are designed but **deliberately deferred to Phase 2+**. Both are *enhancements over working deterministic paths*, so neither blocks current rounds — and both depend on the **Phase 2 LLM adapter**. **Sequencing (decided):** the LLM debuts on **essay generation** (where it's genuinely necessary), proves the call path/adapter there, and only then extends to these matching/canonicalization jobs — added once we can *measure* how much they're actually needed, never bolted onto a page-2 round prematurely. Until then: deterministic ladder + profile-side tiered lists; unmapped/unmatched → empty `needs_review`.

- **LLM semantic field-matching tier.** Unmapped fields currently flag as **empty `needs_review`**. The planned upgrade is an **LLM-semantic-match tier (below fuzzy ≥ 90)** that maps an unrecognized field to a known answer, fills the guess, **and** flags `needs_review` — **guess + fill + flag, never guess + trust** (the same safety contract as the employer match: a model guess is still a guess and always gets a human check). Depends on the Phase 2 LLM adapter; should debut **after** essay generation proves the call path.
- **LLM vocabulary canonicalization.** For choice fields whose form-option vocabulary differs from the profile's wording (e.g. `degree` "Bachelor of Science" → the dropdown's "Bachelors"; `field_of_study`), today's answer is **profile-side tiered candidate lists** (ordered most-specific-first + a fallback like "Other", run through `resolve()` — see Matching strategy + the Education note). The LLM version would *canonicalize* a profile value to the live option set when the tiers miss — but its output is still a **candidate** that must clear the match ladder / land in `needs_review` if not confident (same guess-and-still-flag rule). Enhancement over the working tiered path, so it waits.

## Employer match — "previously employed here?" (safety-critical)

`candidateIsPreviousWorker` sits next to a **truthfulness certification**, and selecting "Yes" unfurls follow-up fields — so a wrong "Yes" is a false legal statement. `decidePreviousWorker(company, questionText, employers)`:
- **clean miss** (no known employer matches) → fill **"No"**, no review (confident non-membership).
- **partial overlap** with the application company → fill **"No" + review** (name overlap may be the same employer).
- **exact company match OR a known employer named in the question text** → fill **"Yes" + review**.
- **unevaluable** (no company set / list unconfigured / `[]`) → **blank + review** — no blind guess.
- **NEVER auto-"Yes" without a review flag.** *Why:* this field is adjacent to a truthfulness certification and a "Yes" unfurls follow-up questions, so a wrong positive is a false legal statement — every "Yes" (and every uncertain "No") gets a mandatory human check, never a silent auto-answer.
- **Question-text scan:** these questions name the entities that count (affiliates/subsidiaries/predecessors — "Elavon, U.S. Bancorp Investments, Union Bank"; "Ken Garff") which the bare `jobContext.company` misses. Scan the question label for each known employer via a **contiguous whole-word token-sequence** match, gated by a distinctiveness check (multi-word, or a lone word ≥5 chars not in `GENERIC_SINGLE`) so a short/common entry ("Bank") can't false-match boilerplate. Works even with `jobContext.company` unset (adds a "no company to corroborate" note). It reads the user's KNOWN employers out of the question — it does NOT extract company names from prose (no LLM).
- **`employment_history_companies` = industry employers ONLY** (companies you were formally employed by; excludes academic/lab/club affiliations). Its completeness is what makes the auto-"No" safe. `["none"]` = "never formally employed" → confident "No"; `[]` = unfilled → flags every such question for review.

## Review summary (the fill → review → submit contract)

Stage 1 of the pipeline. On a **fully-completed** run the engine builds a `reviewSummary` bundle and RETURNS it; `background.js` writes it to `chrome.storage.local` — **only on completion** (a crashed/aborted run writes nothing; no partials).
- **Envelope:** `schema_version`, `page`, `url`, `tenant`, `captured_at`, `total`, `counts` (by fill_status), `by_type`, `needs_review_count`, `entries[]` (every field, page order).
- **Per-field entry:** `field_id`, `page`, `field_index`, `question_label`, `widget_type`, `canonical_field`, `is_required`, `current_value` (the value actually filled — selected option text for choice widgets, only when filled), `original_ai_value` (the bot's pick at write time, never changed by edits), `is_edited`, `edit_kind` (`override` / `filled_blank` / `cleared` / `null` — provenance for the later replay), `confidence` (high/medium/low/none) + `confidence_source` (the tier), `needs_review` + `needs_review_reason`, `fill_status` (filled/not_filled/skipped/error) + `fill_error`, `detail`, `match_tier`, `options` (full list, plain dropdowns), `captured_options` (the partial filtered set, typeaheads), `character_count` (reserved).
- **Required-field escalation:** a required field left unfilled surfaces in review (highest-value review item — and, multi-page, it blocks page advancement).
- **Viewer/editor** (`summary.html`/`summary.js`, opened via popup "View last summary"): NEEDS REVIEW first, then ALL FIELDS. **M14 — choice fields are editable**: plain dropdown → `<select>` from the full `options`; typeahead/source → pick-list from the (partial) `captured_options`/`options` + an explicit "matched the original search — edit on the form for other values" note (degrades to value+note when ≤2); text/radio/checkbox display-only. Edits write back into the SAME record (`current_value`=pick, `original_ai_value` preserved, `is_edited`/`edit_kind` set), persisted to storage, updated in place (no re-render → no scroll jump).

## Multi-page — M15 built ONE transition; the full N-page loop is next round

Workday applications span several pages (My Information → Experience → Questions → … → Review). **M15 makes the walk survive exactly ONE transition** (fill page 1 → Next → re-inject → fill page 2, hard 2-page cap), live-verified on LiveRamp wd5. Generalizing to N pages + the accumulation decision below is the next round. Ported from the proven Python implementation, adapted to the MV3 runtime. The walk lives in `runWalk` (`background.js`); the engine gained only a read-only `nav` block on its return.

### Core constraint: the engine is torn down on every page transition
The injected engine's context is destroyed when the page navigates, so the loop **cannot live in the engine** — it lives in the **service worker** (`runWalk`, persists across navigations) and **re-injects the engine into the ACTIVE tab on each page** (same active-tab injection as today — NOT a background tab; background-tab automation stays deferred, see Architecture). Per-page flow (as built): SW injects `fillEngine` → engine fills + records + returns `nav` metadata → SW persists the bundle → **SW clicks Next** (injected `clickNext`, NOT the engine) → page navigates (engine dies) → SW waits for the new page → SW re-injects → repeat. *(New vs Python: SW re-injection across transitions is the extension-specific mechanism; the Python tool drove a persistent Playwright page and never lost context.)*

**Decided (M15): the SW clicks Next, not the engine.** The engine only REPORTS `nav.nextButtonPresent` / `nav.reviewPagePresent`; the SW does a separate guarded `clickNext` injection AFTER the fill result is captured + persisted — so triggering navigation can never drop the just-filled page's review data.

### Per-page transition wait — poll-by-reinjection (handles the re-injection race)
Each re-injection risks the **engine-not-ready race** from early M10 — injecting before the new page's DOM is ready. Fix (built as `waitForNextPage`): after `clickNext`, the SW re-injects a tiny `probePage` every ~400ms (15s ceiling) until the page **signature** differs from the prior page AND the new page is hydrated (`readyState==='complete'`, ≥1 `formField-*`) AND the field count holds steady across two reads. **Injection errors mid-navigation are treated as "not ready, keep polling"** (not a failure). Runtime-agnostic — works for both hard navigations and SPA soft-nav, per page (not just the first).
**Signature = `url || pageId || formFieldIds` (any one differing = advanced).** ⚠️ `pageId` alone is NOT sufficient: on LiveRamp wd5 the container `applyFlowPage` is **shared across pages**, so the **`formField-*` set delta** is the load-bearing signal (see docs/dom-patterns.md 2026-06-03).

### Termination: stop at the review page, NEVER submit (double guard — BUILT)
Review-page marker: `data-automation-id="applyFlowReviewPage"`. The footer **Next button reuses the same `data-automation-id` as Submit** on the review page, so the walk must never click the footer button once the marker is present. **Double guard implemented (M15):** (1) `runWalk` stops if `nav.reviewPagePresent` (never advances onto/past review), AND (2) `clickNext` itself returns `{refused:"review-page"}` without clicking if the marker is present — defense in depth on the one click that could submit an application. Plus a **hard `MAX_PAGES` cap** (2 this round) so a detection bug can't loop forever. (M15's single click is on page 1 by construction; the guard is foundation for the N-page loop.)

### Required fields block advancement → graceful halt
A required field the engine can't confidently fill **blocks Next** (Workday won't advance with a required field empty). As built: the page signature never changes, `waitForNextPage` times out, and the walk **halts gracefully with `stoppedReason: "nav-timeout"`** — it does NOT error, does NOT guess. Recording WHICH field blocked it into the summary is the next round (the graceful halt is free now); this is why `is_required` accuracy matters.

### The review summary must ACCUMULATE across pages — STILL THE OPEN DECISION
M13's `reviewSummary` is single-page (one object). **M15 interim: overwrite-per-page** — each completed page writes `reviewSummary`, so a two-page walk ends holding the LAST page; page 1 is not retained. This is deliberate scaffolding, NOT the answer. The N-page round must accumulate each page's per-field results into ONE whole-application summary (each entry already carries its `page`).
**Open decision — resolve FIRST thing in the N-page round:** (A) accumulate in SW memory, write to storage only on completion — no partials (matches today's "a crashed run writes nothing" rule), but risks loss if the SW is evicted mid-walk; vs (B) write incrementally per page — robust to eviction, but reintroduces partial summaries. *(Python accumulated into a run-folder on disk and leaned partial-bundle-on-abort, closer to (B).)*

### Ports from Python vs new in the extension
- **Ports (done in M15):** the review-page marker (`applyFlowReviewPage`), the double Submit-guard.
- **New (extension runtime, done in M15):** SW re-injection into the ACTIVE tab across transitions (not background tabs); the poll-by-reinjection transition wait; SW-side `clickNext` decoupled from fill.
- **Still to port/decide (N-page round):** summary accumulation in `chrome.storage` (the open decision above; Python used a run-folder); strict-replay SUBMIT.

## Resume upload & storage (M16 — wired into the page fill)

The resume is NOT picked from the OS filesystem per application. *Why:* the product's end state generates a per-application AI-tailored resume variant (or one fixed resume if the user opts out) — both mean the bytes are **held/produced inside the extension**, never file-picked per application (a picker is incompatible with generated variants and hostile to the high-volume queue-and-run premise). So the bytes live in the extension and get attached programmatically.

- **Storage (`db.js`):** the user uploads one PDF in the popup → stored as **base64 in IndexedDB** (DB `ApplyPilot`, store `resume`, single fixed key **`resume:default`** → `{filename, mime, size, base64, savedAt}`). **IndexedDB, not `chrome.storage`** — a real resume's base64 (hundreds of KB to MBs; M16.2 verified 178KB → 237K chars) blows past `chrome.storage` quotas and binary document bytes don't belong there. `db.js` loads in three contexts off ONE file: popup `<script>`, SW `importScripts`, Node `require` (UMD-lite bottom guard) — the last is what makes the storage helpers unit-testable (`test/db.test.js`, fake-indexeddb). **Phase 2+ (AI-tailored per-application variants) just adds more keys to this same store — do NOT pre-build variant slots or per-application keying.**
- **Attach (proven M16.1 → M16.2):** Playwright's `set_input_files` does NOT port — an injected fn has no filesystem, and **a `File`/`Blob` can't cross the injection/message boundary (serializes to `{}`)**. So: the SW reads the base64 from IndexedDB and passes it as a **plain STRING arg** into the injected fn (`attachResume(base64, filename, mime)`), which rebuilds the `File` in the page, sets `input.files` via a `DataTransfer`, and dispatches `change`. **Strings only across the boundary — never a File/Blob.** Workday's React `onChange` (delegated) fires; no drop-event fallback needed.
- **Success signal:** `input.files` **RESETS to 0** after Workday's XHR upload, so success is read from the confirmation ROW, not the input. The wire-into-fill round should gate specifically on **`file-upload-successful`** (M16.2 saw the poll match `file-upload-item` first, before the success marker rendered). See dom-patterns 2026-06-03.
- **Wired into the page fill (M16.3):** the engine reports `nav.uploadWidgetPresent` (a `file_upload` widget type for `input[type=file]`); the SW post-fill step **`attachResumeForPage`** (runs in BOTH `RUN_FILL` and the walk) reads the stored resume and injects **`attachResume`**, which **clears existing attachments** (one-at-a-time, re-resolving the section/items/`delete-file` **fresh from `document` each pass** — Workday swaps the section subtree mid-loop, so a captured ref goes stale and caps deletion at n−1), attaches, and **gates on `file-upload-successful`**. On a confirmed attach the SW patches the persisted bundle's `file_upload` entry to `filled`. The throwaway "Test resume attach" button/`TEST_ATTACH` were removed; the resume **upload** control stays.

## Repeating sections — Work Experience / Education / Websites / Languages / Certifications (M17+)

Page 2 (My Experience) has repeating multi-field sections, all driven by `fillRepeatingSection` (reconcile to **exactly N**: Add→mount up to N, **delete trailing extras** beyond N via `deleteEntryButton` (M21), then fill each — true idempotency). The per-entry fill is **`fillMappedEntry(entry, item, idx, entrySel, fieldMap, sectionName)`** (M20) — config-driven over a `fieldMap` of `{field|labelRegex, name, widget, key, path}`: `year`→year-only `fillDateComposite`; `checkbox`→reconcile to a boolean (label-activation); `text`/`dropdown`/`typeahead`→`resolve()` (tiered-array passthrough)→the matching handler. **Field resolution is by `field` (automation-id) OR `labelRegex`** — the latter for sections with **hashed `formField-*` ids** (M22 Languages' proficiency dropdowns). Work Experience keeps its bespoke `fillWorkExperienceEntry` (checkbox-reconcile/dates/role-description). Sections = a `*_MAP` + a `fillRepeatingSection` config:
- **Education** (`EDUCATION_MAP`): school / degree / fieldOfStudy / **gradeAverage→gpa** / from-to years.
- **Websites** (`WEBSITE_MAP`): `webAddress-N--null`, one `url` text field ← `profile.websites[].url` (run through `ensureHttps`).
- **Languages** (`LANGUAGE_MAP`, M22): `language` dropdown + reading/speaking/writing **Proficiency dropdowns resolved BY LABEL** (hashed ids) + a final `native` checkbox that's **checked when all three are Fluent** (`_allFluent` = `isFluent` × 3, computed SW-side; processed LAST so the proficiency fills are recorded before checking, in case it hides them). Uses **`deleteOnNoMatch: true`** — an optional pick-section where a required pick that can't match an option would block Next, so the entry is **deleted** instead (sweep after fill; `ok` = every required rec filled). WE/Education/Websites keep it off (flag for review, never delete).
- **Certifications** (`CERTIFICATION_MAP`, M23a): `certification` **typeahead** (required pick) + `certificationNumber` text + `issuedDate`/`expirationDate` **full M/D/Y `date` composites** (`fillDateComposite` gained a `dateSectionDay-input` segment; the `date` widget is fed a SW-parsed `{month,year,day}` from **`parseYearMonthDay`** in `lib.js`). Attachments file field omitted. `deleteOnNoMatch: true`. **NOTE: this section's `certification` typeahead inherits the M22-original `fillTypeahead`, which does NOT work on the Magna tenant (see "Typeahead — Magna rework PENDING" below) — so the cert won't commit on Magna until that rework lands.**

The load-bearing DOM facts (LiveRamp recon, see dom-patterns 2026-06-04):
- **Each entry is a `<div data-fkit-id="workExperience-N--null">`** (N is a Workday internal index, not sequential), mounted **inline** (no modal).
- **🔑 `formField-*` ids are DUPLICATED across entries** (`formField-jobTitle`, `formField-companyName`, … repeat per entry — NOT indexed). So a document-wide `querySelector('[data-automation-id="formField-jobTitle"]')` only ever finds entry 1. **Every field access MUST scope to the entry container.** This is why the flat driver loop **skips any `formField-*` inside a `[data-fkit-id^="workExperience-"]` container** — `fillWorkExperience` owns those (else they'd double-record as "no mapping").
- **⚠️ Entry-container selector — the date wrappers share the prefix.** The From/To date wrappers are `data-fkit-id="workExperience-N--startDate"` / `--endDate`, so a bare `[data-fkit-id^="workExperience-"]` over-matches (one entry → 3 nodes: the container + its 2 date wrappers), which inflates the entry count and breaks the fill loop. **Entry containers are the `--null` ones** → enumerate with `[data-fkit-id^="workExperience-"][data-fkit-id$="--null"]`. (The flat-loop skip-guard stays the *broad* prefix — it SHOULD skip the date wrappers too. M17 dodged this by only using `entries[0]`; M18 surfaced + fixed it.)
- **Add buttons share `data-automation-id="add-button"`** across all sections (text "Add" to create the first entry, "Add Another" when ≥1) — can't target by id; anchor on the section **heading** (`findSectionAdd(headingRegex)`). The generic **`fillRepeatingSection({ name, headingRegex, containerPrefix, items, fillEntry })`** (used by both WE and Education) clicks Add to reach `N = items.length` entries (waiting for the entry-container count to rise after each click, capped), then fills each `entries[i]` via the section's `fillEntry(entry, item, i, entrySel)` (re-resolving `entries` fresh each iteration — selections/toggles re-render). `items` is the **SW-prepared** list (`meaningfulEntries(arr, keys)`, pure+tested in `lib.js`). **Idempotency = add-only** (re-run with ≥N entries adds nothing); **delete-extras** (entries > N) is deferred. The **create-first Add** path is exercised by Education (starts empty); WE's first entry is always present.
- Per-entry profile mapping is array-indexed (`work_experience[i].job_title`, `education[i].degree`, …) — dedicated `WORK_EXPERIENCE_MAP` / `EDUCATION_MAP`, not the flat singular `FIELD_MAP`. The SW's **`prepareProfile`** pre-filters BOTH `work_experience` and `education` to meaningful entries + annotates parsed values, so the engine's `profile.work_experience` / `profile.education` ARE the lists to fill.
- **Date composite (M17-date):** `From*`/`To*` are a `dateInputWrapper` with two `role="spinbutton"` `<input>`s — `dateSectionMonth-input` (1–12) + `dateSectionYear-input`. The profile `"YYYY-MM"` is parsed **in the SW** by the pure, unit-tested `parseYearMonth` (`lib.js`; rejects the literal `"YYYY-MM"` placeholder + out-of-range) and passed to the engine as `fromParsed`/`toParsed` — the injected engine can't `import`, so the *shipping* parser lives where it's requireable. The engine's `fillDateComposite` sets each segment via the proven native-setter+`input`+`change`.
- **"I currently work here" controls the To box** (checked → To removed). `fillWorkExperience` **reconciles the `currentlyWorkHere` checkbox to `currently_work_here` FIRST** (toggle the `<label for>` via label-activation, verify `input.checked`), waits for To to remount when unchecking, re-resolves the entry, then fills dates. `setSearchValue`-style is reused; the checkbox toggle is label-activation like radios.
- **Role Description (M18-role):** a plain `<textarea>` (no automation-id on it — scope via the `formField-roleDescription` wrapper). The profile has no description string, so it's filled from **`bullets` joined with newlines** by the pure, tested `joinBullets` (`lib.js`; computed SW-side as `bulletsText`). A `<textarea>` needs the **`HTMLTextAreaElement` native setter** (not `setSearchValue`, which is input-only) + `input`/`change`. A WE entry is now complete.
- **Education (M19):** entries `education-N--null`; fields `schoolName` (text), `degree` (dropdown), `fieldOfStudy` (typeahead), `firstYearAttended`/`lastYearAttended` (**year-only** date composites — `dateSectionYear-input` alone, so `fillDateComposite(wrapper, null, year)`; `fillDateComposite` takes `month=null` for year-only). `EDUCATION_MAP` routes text/dropdown/typeahead through **`resolve()`** so `degree`/`field_of_study` can be **PROFILE-side tiered candidate lists** (ordered most-specific-first + a fallback like `"Other"`, e.g. `degree: ["Bachelor of Science","Bachelors"]` — the dropdown only offers "Bachelors"). ## CDP off-loop actuation (M24) — filling while the tab is hidden

A hidden/minimized tab throttles page timers to ~1Hz then deep-freezes, so the page-injected fill stalls (proven by live instrumentation; a PASSIVE debugger attach does NOT relieve it). The fix: issue actuation as **CDP commands from the service worker** (`chrome.debugger`, the `"debugger"` permission) — CDP `Input.*`/`Runtime.evaluate` execute off the page loop and are throttle-immune. Workday's debounced REACTION to that input still runs page-side and throttled → **all waits are generous SW-side wall-clock; Δperf ~1000ms during a run is EXPECTED, never failure**. Live-verified end-to-end on Magna wd3, window minimized (10 fields filled + read-back-verified). Full empirical detail: dom-patterns 2026-06-12.

- **Substrate/brain split (the substrate-swap hedge):** `cdp.js` = the substrate — attach/detach lifecycle (detach in `finally`; external-detach/tab-close listeners; **ONE debugger client per tab**, so page DevTools on the tab kills the attach), trusted input primitives, `cdpEval` DOM reads, the hidden-gate — plus `makeCdpActuation()` implementing the actuation interface. `fill-driver.js` = the brain (`drivePageFill`): the **M22 decision logic VERBATIM** (`FIELD_MAP`/`resolve`/employer-match/record+status semantics) calling ONLY the interface — Node-testable with a fake actuation (`test/fill-driver.test.js`, incl. the NAMED invariant test that the previous-worker radio is never left "Yes" without a review flag). ALL pacing goes through `act.delay` (SW wall-clock) — **never a page-side timer**; every element is re-resolved fresh per call (React re-renders orphan held nodes — recon-proven).
- **Dropdown commit = type-to-highlight + VERIFIED Enter, NOT a click.** CDP clicks a COORDINATE, not an element; an out-of-view option's rect lands outside the popup → outside-click dismissal (the "Uruguay pitfall" — Playwright's element click auto-scrolled and hid this). Flow: open (click trigger) → settle the **aria-controls-scoped PORTALED** option list (2 equal non-zero reads — render is atomic, but a cold lazy list took ~5.6s hidden → 20s ceiling) → match ladder → type the target's leading chars (native type-jump moves `aria-activedescendant`) → **the highlighted text MUST equal the target before Enter** (arrow-walk correction if the jump lands wrong; never commit unverified) → gate on trigger text == target. ScrollIntoView+coordinate-click survives only as a last resort behind the same gate.
- **Text = `Input.insertText`** (fires trusted `beforeinput`+`input`, value survives blur) after CDP click-to-focus + trusted Ctrl+A/Delete clear; verified by read-back — a mismatch is NEVER reported `filled`. **Radio/checkbox** = coordinate click on the `<label for>` (fallback: focused input + Space), verified via `checked`.
- **Typeahead (M25) = the proven Magna brain on this substrate** (`fillTypeaheadCdp`, fill-driver.js). Per-candidate tier walk; transition-aware settle requiring a FRESH change since the candidate's own filter-Enter (the pre-filter fallback list is STABLE — matching it was the historic false-fill — and a STALE banner survives input clearing); banner (`promptTitle` "No matches found") = HARD BLOCK; match ONLY the current candidate; the ONLY commit signal is the `selectedItem` chip normalize-equal to the matched option — never option text. **Focus hygiene (load-bearing):** a banner DROPS searchBox focus, so before EVERY candidate's clear/type we re-assert + READ-VERIFY `searchBox.focused` (re-open if it unmounted); if focus can't be confirmed → `needs_review` "could not focus — not actuating blind", STOP. Without this, a post-banner Ctrl+A selects the whole PAGE, the query never lands, and the widget's type-ahead-HIGHLIGHT + filter-Enter commits a STRAY row 0 (the live "Afghanistan" stray). **Honesty:** a final chip read → a record never reports `after:null` when the page holds a value (an uncommanded stray is flagged). **Pre-filled guard:** a chip matching a candidate is KEPT with zero actuation (countryPhoneCode is auto-derived from Country — the common case, live-proven incl. surviving a same-value Country re-commit); a mismatched pre-fill is flagged, never overwritten (overwrite = M25.1). **Commit ladder:** single-exact AUTO-COMMITS on the filter-Enter (chip may carry the FULL option name — accepted only on normalize-equality, else flagged); multi-match commits via a **TRUSTED CDP CLICK** on the matched option (text-keyed; short-list proven, long-list UNTESTED — the Uruguay condition) because **NO highlight ever arms under CDP-injected typing** (aria-activedescendant null with insertText AND per-char keystrokes — the spec's second-Enter was a human-typing behavior). Enter is the ONLY filter trigger (typing alone does not filter — verified). Targeted harness: popup "CDP fill one typeahead" (`RUN_CDP_FILL_TA`, label regex, entry-scoped composed selectors).
- **Entry points:** popup **CDP recon** (`RUN_CDP_RECON`) — run FIRST on any new tenant (rect liveness, input/commit paths, latencies, restore-where-possible) — and **CDP fill (hidden)** (`RUN_CDP_FILL`): attach → hidden-gate → drive → **NEEDS-REVIEW-first console report** → detach. **No reviewSummary bundle yet** — console report only; the persisted review UI stays a hard requirement before any ship.
- **Source (M26) = a SEARCH typeahead on Magna** (`fillSourceCdp`, fill-driver.js): the "How did you hear about us?" picker shows ~13 chevron CATEGORY rows on open, but typing into the searchBox FILTERS straight to leaves — so it's driven like the typeahead (categories bypassed). Mirrors the M25 walk (focus hygiene, transition settle, banner block) with source deltas: leaves = `promptOption` + `data-automation-label` (NOT role=option), **chip-excluded** (a committed chip elsewhere embeds a promptOption — the contamination that cost a recon round); commit-verify = the matched leaf's `promptLeafNode` `multiselectlistitem-isselected` flip OR a `selectedItem` chip. Candidates from `defaults.how_did_you_hear` (preferred + fallback). Wired into `drivePageFill`. Live-verified hidden (LinkedIn auto-commits; the multi-match trusted-click + promptLeafNode-verify are unit-tested but not yet live-proven).
- **Still deferred (honest `needs_review`/untouched):** the tree/EXPAND-WALK picker shape (NO searchBox → chevron categories you drill into) + Magna's Certification TREE — only needed when a tenant without a searchBox is observed; the in-tree page-substrate `fillSource` covers the expand-walk on the page path. Also deferred: repeating sections and the multi-page walk on CDP.

## Working principles

- **Trace the real DOM before writing a handler — don't guess.** Every hard bug (the `source` picker, the dropdown chip contamination) only cracked after blind guesses failed and we instrumented a read-only trace of the *actual* DOM, then built from what it showed. Guessing widget shapes wasted rounds; tracing settled them — make a discovery trace the first step on any new widget/tenant.
- **Incremental:** one focused change per milestone, verified on a real page. No skipping ahead.
- **Observation-driven:** rules in `docs/dom-patterns.md` come from observed DOM, not assumptions; keep code and doc in sync.
- **Don't port the Python repo blindly:** it's a design reference (intent, prompts, edge cases), not code to mechanically translate to JS.
- **Commit per milestone:** each working milestone gets a commit, so we can bisect when something breaks.
- **Three consoles:** service worker (`background.js` + the engine's returned data), page F12 (anything `console.log`'d inside the injected function), popup right-click → Inspect (`popup.js`). Most `[ApplyPilot]` output is in the service-worker console.
